Avisos y descargas en segundo plano en el proyecto

El Atlas 3D aprende a avisar y a descargar en segundo plano: las fichas de los modelos se guardan para usarse sin conexión, con una barra de progreso y un aviso cuando terminan. Es el espejo de la Sesión 26 aplicado al proyecto — con una diferencia que importa: aquí el Service Worker pasa por Vite, y el código se comparte en vez de duplicarse.

Objetivos de aprendizaje

  • ✓Reescribir el Service Worker del Atlas con strategies: "injectManifest" en vite-plugin-pwa, sin perder el precaché.
  • ✓Compartir una misma función de descarga entre el Service Worker y la página, aprovechando que Vite empaqueta ambos.
  • ✓Implementar una cola de descargas con Background Sync, progreso visible y notificación solo cuando el usuario no está mirando.
  • ✓Decidir con honestidad qué se puede aplicar de la Sesión 26 a un proyecto sin servidor, y qué no.

Recursos de esta sesión

  • Descargar .zipCheckpoint — cierre de la Sesión 36. El Atlas 3D con visor de Three.js (cubo de prueba), sensores de orientación y cámara de fondo, con el Service Worker generado por vite-plugin-pwa. Hoy le agregamos sw.ts, descargas.ts y avisos.ts, y las fichas de public/modelos/.

1Esto ya lo viste a fondo en la Sesión 26

Las tres promesas de la Notification API, la Push API y Background Sync, el permiso pedido en contexto, el significado de default/granted/denied, VAPID y el flujo de un push, InjectManifest como idea, la bandeja de salida, el reintento por excepción, la idempotencia y el plan B para Safari y Firefox, se estudiaron a fondo en la Sesión 26, sobre el Gestor de Tareas. Aquí no se repiten.

Hoy importa lo que cambia al llevarlo al Atlas 3D. Dos diferencias de fondo: (1) el Atlas no tiene servidor, y (2) el Atlas pasa por Vite, así que su Service Worker se empaqueta como cualquier otro módulo.

2Qué se aplica del Gestor y qué no: la honestidad primero

El título de la sesión dice «push», pero un push exige un servidor que envíe el mensaje, y el Atlas no tiene ninguno: todo su estado vive en el dispositivo. Fingirlo —por ejemplo, mostrando una notificación «push» que en realidad se dispara desde la propia página— sería engañar. Lo que sí tiene sentido aplicar es lo otro de la Sesión 26: notificaciones locales y Background Sync.

Pero el Gestor usaba Background Sync para enviar tareas a un servidor, y el Atlas no tiene a dónde enviar. Su equivalente natural es el sentido contrario: descargar. El Atlas va a ofrecer «Descargar fichas para usar sin conexión», y esa descarga puede quedar pendiente si no hay red y terminarse más tarde. Es el mismo mecanismo (cola persistente + evento sync) con la dirección invertida.

Lo que se descarga son fichas de texto, no modelos 3D. Los archivos de public/modelos/*.json son tres fichas breves (patrón MVC, arquitectura en capas, microservicios) con resumen, componentes, cuándo usarlas y su riesgo principal. El catálogo real de modelos .glb todavía no existe; inventar archivos 3D falsos sería lo contrario de lo que enseñó la Sesión 33. Las fichas son contenido real de estudio, no relleno.

3De generateSW a injectManifest en Vite

Hasta la Sesión 36, vite-plugin-pwa usaba su modo por defecto: generateSW (Workbox escribe el Service Worker). Para escribir el nuestro basta cambiar la estrategia y decirle dónde está el archivo:

vite.config.ts
    VitePWA({
      // El manifest ya existe a mano desde la Sesión 27 (public/manifest.json,
      // enlazado en index.html) — aquí solo se gestiona el Service Worker.
      manifest: false,
      registerType: "autoUpdate",
      injectRegister: false, // registramos nosotros mismos en main.ts, con virtual:pwa-register

      // Sesión 37: de generateSW (Workbox escribe el SW) a injectManifest (TÚ
      // escribes src/sw.ts y el plugin solo le inyecta la lista de precaché).
      strategies: "injectManifest",
      srcDir: "src",
      filename: "sw.ts",
      injectManifest: {
        globPatterns: ["**/*.{html,js,css,png,json}"],
        // Las fichas de modelos NO se precachean: se descargan bajo demanda.
        // Sin esta línea, el patrón **/*.json las metería en el precaché y
        // la descarga «voluntaria» no tendría sentido.
        globIgnores: ["modelos/**"],
      },
    }),

Con generateSW las reglas de caché en tiempo de ejecución se declaraban en un bloque runtimeCaching; aquí ya no existe. Con injectManifest el plugin no genera reglas: las escribes tú en sw.ts. Y fíjate sobre todo en globIgnores:

Un error silencioso que esta línea evita. El patrón **/*.{html,js,css,png,json} incluye los .json. Sin globIgnores: ["modelos/**"], las fichas entrarían en el precaché: se descargarían todas con la primera visita y el botón «Descargar» no tendría ningún sentido, porque todo ya estaría descargado. No habría ningún error: simplemente una función que no hace nada. Se detecta mirando el número de entradas del precaché al compilar: 8 con la exclusión (513,93 KiB) y 11 sin ella (515,82 KiB), medido quitando la línea.

import { registerRoute } from "workbox-routing";
import { CacheFirst, NetworkFirst } from "workbox-strategies";
import { ExpirationPlugin } from "workbox-expiration";
import { clientsClaim } from "workbox-core";
import { abrirBaseDeDatos } from "./db";
import { descargarPendientes, ETIQUETA_SYNC } from "./descargas";

declare const self: ServiceWorkerGlobalScope;

// Background Sync no está en los tipos estándar de TypeScript: se declara lo mínimo que usamos.
interface SyncEvent extends ExtendableEvent {
  readonly tag: string;
  readonly lastChance: boolean;
}

// Con registerType:"autoUpdate" y un SW propio, activar la versión nueva
// es TU trabajo (con generateSW lo hacía el plugin).
self.skipWaiting();
clientsClaim();
cleanupOutdatedCaches();
precacheAndRoute(self.__WB_MANIFEST);

registerRoute(
  ({ url }) => url.pathname.startsWith("/iconos/"),
  new CacheFirst({
    cacheName: "imagenes",

  })

Cuatro cosas que cambian respecto al Gestor:

  • Imports normales. Vite empaqueta sw.ts, así que import { precacheAndRoute } from "workbox-precaching" funciona. No hay copyLibraries ni importScripts. Eso sí: hay que declarar esos paquetes como dependencias (npm i -D workbox-core workbox-precaching workbox-routing workbox-strategies workbox-expiration).
  • skipWaiting() y clientsClaim() son tuyos. Con registerType: "autoUpdate" y un Service Worker propio, el plugin ya no los añade por ti.
  • Tipos de TypeScript aparte. El Service Worker usa la librería WebWorker, no DOM; mezclarlas en un mismo tsconfig hace chocar self. Por eso tsconfig.json excluye src/sw.ts y un tsconfig.sw.json lo revisa aparte; el script build pasó a ser tsc && tsc -p tsconfig.sw.json && vite build.
  • El evento sync no está en los tipos estándar de TypeScript; se declara a mano la interfaz mínima (tag y lastChance).

4Una función, dos contextos

En el Gestor (Sesión 26) la lógica de envío existía dos veces: una en el SW y otra en la página para el plan B, porque un Service Worker clásico no puede importar módulos ES. En el Atlas, Vite empaqueta ambos, así que la función de descarga se escribe una vez y la importan los dos:

src/descargas.ts (constantes)
export const ETIQUETA_SYNC = "descargar-modelos";
export const CACHE_MODELOS = "modelos-3d";
export const urlDeModelo = (id: string) => `/modelos/${id}.json`;
src/descargas.ts (la función compartida)
export type AlProgresar = (hechos: number, total: number) => void | Promise<void>;

/**
 * Descarga, una por una, las fichas que están «pendiente». Si una falla LANZA:
 * las anteriores ya quedaron marcadas como «listo» (no se vuelven a pedir) y
 * el navegador reintentará solo las que faltan.
 * Devuelve cuántas se descargaron en esta pasada.
 */
export async function descargarPendientes(db: IDBDatabase, alProgresar: AlProgresar): Promise<number> {
  const todas = await obtenerDescargas(db);
  const total = todas.length;
  let hechos = todas.filter((d) => d.estado === "listo").length;
  const cache = await caches.open(CACHE_MODELOS);
  let descargadas = 0;
  for (const d of todas.filter((x) => x.estado === "pendiente")) {
    // cache: "reload" evita que la caché HTTP del navegador responda por la red.
    const resp = await fetch(urlDeModelo(d.modeloId), { cache: "reload" });
    if (!resp.ok) throw new Error(`${d.modeloId}: el servidor respondió ${resp.status}`);
    await cache.put(urlDeModelo(d.modeloId), resp);
    await marcarDescargaLista(db, d.modeloId);
    hechos++;
    descargadas++;
    await alProgresar(hechos, total);
  }
  return descargadas;
}

Puntos finos: si una ficha falla, la función lanza, pero las anteriores ya quedaron marcadas como «listo», así que el reintento solo pide las que faltan (se comprueba en la sección 8, escenario C). Y cache: "reload" evita que la caché HTTP del navegador responda en lugar de la red, que daría la falsa impresión de «descargado» sin haber consultado al servidor.

5La cola: una migración más

Igual que en el Gestor, el almacén nuevo (descargas) obliga a subir la versión de la base a 2 con migración por tramos; quien venía de la versión 1 conserva su progreso, sus favoritos y sus notas cifradas:

src/db.ts (cola)
export interface Descarga {
  modeloId: string;
  estado: "pendiente" | "listo";
}
src/db.ts (cola)
/** Anota (o reinicia a «pendiente») la descarga de varios modelos. */
export function encolarDescargas(db: IDBDatabase, ids: string[]): Promise<void> {
  return new Promise((resolve, reject) => {
    const tx = db.transaction("descargas", "readwrite");
    const store = tx.objectStore("descargas");
    ids.forEach((modeloId) => store.put({ modeloId, estado: "pendiente" } satisfies Descarga));
    tx.oncomplete = () => resolve();
    tx.onerror = () => reject(tx.error);
  });
}
src/db.ts (cola)
export function obtenerDescargas(db: IDBDatabase): Promise<Descarga[]> {
  return new Promise((resolve, reject) => {
    const peticion = db.transaction("descargas", "readonly").objectStore("descargas").getAll();
    peticion.onsuccess = () => resolve(peticion.result as Descarga[]);
    peticion.onerror = () => reject(peticion.error);
  });
}
src/db.ts (cola)
export function marcarDescargaLista(db: IDBDatabase, modeloId: string): Promise<void> {
  return new Promise((resolve, reject) => {
    const tx = db.transaction("descargas", "readwrite");
    tx.objectStore("descargas").put({ modeloId, estado: "listo" } satisfies Descarga);
    tx.oncomplete = () => resolve();
    tx.onerror = () => reject(tx.error);
  });
}

6El evento sync del Atlas: avisos con criterio

src/sw.ts (ruta de las fichas)
// Las fichas /modelos/*.json NO están en el precaché (se excluyeron en
// vite.config.ts): solo entran a la caché «modelos-3d» cuando el usuario las
// descarga. Mientras no estén ahí, esta ruta las pide a la red; si ya están,
// responde desde la caché aunque no haya conexión.
registerRoute(
  ({ url }) => url.pathname.startsWith("/modelos/"),
  async ({ request }) => {
    const guardada = await caches.match(request, { cacheName: "modelos-3d" });
    return guardada ?? fetch(request);
  }
);
src/sw.ts (aviso a las ventanas)
async function avisarALasVentanas(mensaje: unknown): Promise<readonly WindowClient[]> {
  const ventanas = await self.clients.matchAll({ type: "window" });
  ventanas.forEach((v) => v.postMessage(mensaje));
  return ventanas;
}
src/sw.ts (sync)
self.addEventListener("sync", (event) => {
  const syncEvent = event as SyncEvent;
  if (syncEvent.tag !== ETIQUETA_SYNC) return;
  syncEvent.waitUntil(
    (async () => {
      const db = await abrirBaseDeDatos();
      try {
        const n = await descargarPendientes(db, async (hechos, total) => {
          await avisarALasVentanas({ tipo: "progreso", hechos, total });
        });
        if (n === 0) return;
        const ventanas = await avisarALasVentanas({ tipo: "descarga-completa" });
        // Notificación solo si NO hay ninguna ventana visible.
        if (!ventanas.some((v) => v.visibilityState === "visible")) {
          await self.registration.showNotification("Modelos listos", {
            body: "Las fichas ya están en tu dispositivo: puedes consultarlas sin conexión.",
            icon: "/iconos/icon-192.png",
            tag: "atlas-descarga",
            data: { url: "/" },
          });
        }
      } catch (err) {
        // lastChance: el navegador ya no reintentará. Es el momento de decirle
        // al usuario que NO pudo completarse (si no, el fallo sería silencioso).
        if (syncEvent.lastChance) {
          await self.registration.showNotification("No se pudo completar la descarga", {
            body: "Abre el Atlas con conexión y vuelve a pulsar «Descargar».",
            icon: "/iconos/icon-192.png",
            tag: "atlas-descarga",
            data: { url: "/" },
          });
        }
        throw err; // relanzar: así el navegador sabe que falló y reintenta
      } finally {
        db.close();
      }
    })()
  );
});

La mayor diferencia con el Gestor está en el catch. Un fallo de sincronización es silencioso por defecto: el navegador reintenta sin que nadie lo sepa, y si deja de reintentar, el usuario nunca se entera de que su descarga no terminó. El evento trae lastChance, que vale true en el último intento. Ahí —y solo ahí— se muestra «No se pudo completar la descarga». Antes de eso, notificar cada fallo sería ruido. Y se vuelve a lanzar el error, para que el navegador sepa que sí falló.

El resto sigue la regla de la Sesión 26: durante la descarga se mandan mensajes de progreso a las ventanas abiertas (la página pinta la barra); la notificación del sistema solo sale si ninguna ventana está visible. La ruta para /modelos/ (arriba) primero busca en la caché modelos-3d y, si no está, va a la red: así una ficha descargada se sirve aunque no haya conexión, y una no descargada sigue funcionando en línea. Y el clic en la notificación usa el mismo manejador de la Sesión 26:

src/sw.ts (clic)
// ── Clic en una notificación: enfocar la app abierta o abrirla ─────────────
self.addEventListener("notificationclick", (event) => {
  event.notification.close();
  const destino = new URL(event.notification.data?.url ?? "/", self.location.origin).href;
  event.waitUntil(
    (async () => {
      const ventanas = await self.clients.matchAll({ type: "window", includeUncontrolled: true });
      const abierta = ventanas.find((v) => new URL(v.url).origin === self.location.origin);
      if (abierta) return abierta.focus();
      return self.clients.openWindow(destino);
    })()
  );
});

7La página: botones, progreso y avisos de ciclo de vida

src/main.ts (descargar)
btnDescargar.addEventListener("click", async () => {
  await dbLista;
  await encolarDescargas(db, MODELOS_IDS);
  pintarProgreso(0, MODELOS_IDS.length);
  btnDescargar.disabled = true;
  try {
    let enSegundoPlano = false;
    if ("serviceWorker" in navigator && "SyncManager" in window) {
      try {
        const reg = await navigator.serviceWorker.ready;
        await (reg as ServiceWorkerRegistration & { sync: { register(tag: string): Promise<void> } }).sync.register(ETIQUETA_SYNC);
        enSegundoPlano = true;
        estadoDescargaEl.textContent = "Descarga solicitada: el navegador la completará en cuanto haya conexión.";
      } catch {
        // Tener SyncManager no basta: register() falla (NotAllowedError) si el
        // usuario bloqueó la sincronización en segundo plano para este sitio.
        enSegundoPlano = false;
      }
    }
    if (!enSegundoPlano) {
      // Plan B (Safari, Firefox, o permiso denegado): se descarga desde la página, con la pestaña abierta.
      await descargarPendientes(db, pintarProgreso);
      await refrescarDescargados();
      render();
    }
  } catch (err) {
    estadoDescargaEl.textContent = "No se pudo completar la descarga: " + (err instanceof Error ? err.message : String(err));
  } finally {
    btnDescargar.disabled = false;
  }
});

Las notificaciones locales del Atlas pasan por un módulo pequeño, avisos.ts, que solo muestra algo si el permiso ya fue concedido:

src/avisos.ts
/** Muestra una notificación a través del Service Worker (funciona también en Android). */
export async function mostrarAviso(titulo: string, cuerpo: string, url = "/", tag = "atlas-aviso"): Promise<boolean> {
  if (estadoAvisos() !== "granted") return false;
  const reg = await navigator.serviceWorker.ready;
  await reg.showNotification(titulo, {
    body: cuerpo,
    icon: "/iconos/icon-192.png",
    tag,
    data: { url },
  });
  return true;
}

El botón de descarga repite la doble salida de la Sesión 26: si register() falla —por no existir SyncManager, o por un permiso bloqueado—, la descarga corre en la página. Además, tres avisos de ciclo de vida de la PWA:

  • «La app ya funciona sin conexión»: registerSW ofrece el callback onOfflineReady, que se dispara cuando el precaché quedó completo por primera vez. Se muestra en pantalla; la notificación del sistema solo si la página no está visible.
  • «Atlas 3D instalado»: el evento appinstalled de la ventana. Aquí sí tiene sentido una notificación: el usuario acaba de pasar a otra ventana.
  • Abrir una ficha desde la notificación: el aviso lleva data.url = "/?modelo=ID"; al cargar, la página lee ese parámetro y resalta la tarjeta correspondiente.

Qué demuestra: (1) la migración conserva el progreso previo; (2) las fichas no están en el precaché antes de descargar; (3) la descarga avanza 1→2→3 con mensajes de progreso y deja las tres en la caché y marcadas en IndexedDB; (4) con el servidor apagado la app recarga y la ficha descargada se sirve; (5) si una ficha falla, las demás quedan guardadas y el reintento pide solo la que faltaba (una sola petición); (6) en el último intento se avisa del fallo; (7) los dos planes B funcionan (sin SyncManager y con el permiso bloqueado); (8) cuando no queda ninguna ventana del Atlas abierta, la notificación «Modelos listos» sí aparece.
Límites honestos de esta prueba. (1) El evento sync se disparó a mano con ServiceWorker.dispatchSyncEvent en los escenarios de fallo; en el escenario normal Chromium lo disparó solo al registrar, porque había red. (2) El 404 se provocó renombrando una ficha dentro de dist/; no se cortó la red de un dispositivo. (3) El clic en la notificación se simuló despachando un NotificationEvent dentro del SW. (4) appinstalled se disparó como evento sintético: no se instaló la app de verdad. (5) No hay push porque no hay servidor, y no se probó en teléfono real ni en iOS. (6) Chromium sin pantalla siempre ve la página «visible»; la rama «hay ventana visible» se comprobó con la página abierta, y la rama «no hay ventana» cerrando la página y despachando el evento desde otra pestaña.

¿Cuándo NO notificar?

EN PAREJAS · 20 MIN

El Atlas notifica en estas situaciones: confirmación de «Avisos activados», descarga completa (solo con la app oculta), fallo definitivo de descarga, instalación de la app, y «lista sin conexión» (solo si la página no está visible). Propongan un aviso adicional que sí aportaría valor y otro que sería ruido, y justifiquen ambos con la regla «una notificación se justifica cuando el usuario no está mirando y necesita enterarse».

Resumen de la sesión

  • Lo conceptual de avisos, push y Background Sync se estudió en la Sesión 26; hoy se aplica a un proyecto sin servidor y empaquetado por Vite.
  • Sin servidor no hay push: se aplican notificaciones locales y Background Sync, este último invertido (descargar en vez de enviar).
  • strategies: "injectManifest" deja el SW en src/sw.ts; globIgnores: ["modelos/**"] evita que las fichas entren al precaché; skipWaiting() y clientsClaim() pasan a ser responsabilidad propia.
  • Como Vite empaqueta el SW, la función de descarga se escribe una sola vez y la comparten el SW y la página.
  • El fallo de un sync es silencioso: lastChance es el momento de avisar; la notificación del sistema se reserva para cuando no hay ventana visible.
  • Verificado en Chromium: cola, progreso, reintento parcial, uso con el servidor apagado, planes B. No verificado: push real (no existe en el Atlas), instalación real, teléfono, iOS.
