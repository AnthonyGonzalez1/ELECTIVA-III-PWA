Antes de empezar

Esto ya lo viste a fondo en la Sesión 26

Las tres promesas de la Notification API, la Push API y Background Sync, el permiso pedido en contexto, el significado de default/granted/denied, VAPID y el flujo de un push, InjectManifest como idea, la bandeja de salida, el reintento por excepción, la idempotencia y el plan B para Safari y Firefox, se estudiaron a fondo en la Sesión 26, sobre el Gestor de Tareas. Aquí no se repiten.

Hoy importa lo que cambia al llevarlo al Atlas 3D. Dos diferencias de fondo: (1) el Atlas no tiene servidor, y (2) el Atlas pasa por Vite, así que su Service Worker se empaqueta como cualquier otro módulo.
Honestidad primero · 2.1

Sin servidor no hay push

El título de la sesión dice «push», pero un push exige un servidor que envíe el mensaje, y el Atlas no tiene ninguno: todo su estado vive en el dispositivo.

No se hace
Fingirlo —por ejemplo, mostrando una notificación «push» que en realidad se dispara desde la propia página— sería engañar.
Sí se aplica
Lo otro de la Sesión 26: notificaciones locales y Background Sync.
Honestidad primero · 2.2

Background Sync, con la dirección invertida

El Gestor usaba Background Sync para enviar tareas a un servidor, y el Atlas no tiene a dónde enviar. Su equivalente natural es el sentido contrario: descargar.

Pieza de la Sesión 26En el Atlas 3D
Push (un servidor envía el mensaje)No se aplica: no hay servidor.
Notificaciones localesSe aplican.
Background Sync para enviar tareasSe aplica, invertido: «Descargar fichas para usar sin conexión».
La descarga puede quedar pendiente si no hay red y terminarse más tarde. Es el mismo mecanismo (cola persistente + evento sync) con la dirección invertida.
Honestidad primero · 2.3

Qué se descarga de verdad

Lo que se descarga son fichas de texto, no modelos 3D. Los archivos de public/modelos/*.json son tres fichas breves (patrón MVC, arquitectura en capas, microservicios) con resumen, componentes, cuándo usarlas y su riesgo principal.

El catálogo real de modelos .glb todavía no existe; inventar archivos 3D falsos sería lo contrario de lo que enseñó la Sesión 33. Las fichas son contenido real de estudio, no relleno.

Un error silencioso que globIgnores evita

Un error silencioso que esta línea evita. El patrón **/*.{html,js,css,png,json} incluye los .json. Sin globIgnores: ["modelos/**"], las fichas entrarían en el precaché: se descargarían todas con la primera visita y el botón «Descargar» no tendría ningún sentido, porque todo ya estaría descargado. No habría ningún error: simplemente una función que no hace nada.

injectManifest · 3.5

Cuatro cosas que cambian respecto al Gestor

Imports normales

Vite empaqueta sw.ts, así que import { precacheAndRoute } from "workbox-precaching" funciona. No hay copyLibraries ni importScripts. Hay que declarar esos paquetes como dependencias: npm i -D workbox-core workbox-precaching workbox-routing workbox-strategies workbox-expiration.

skipWaiting() y clientsClaim() son tuyos

Con registerType: "autoUpdate" y un Service Worker propio, el plugin ya no los añade por ti.

Tipos de TypeScript aparte

El Service Worker usa la librería WebWorker, no DOM; mezclarlas en un mismo tsconfig hace chocar self. Por eso tsconfig.json excluye src/sw.ts y un tsconfig.sw.json lo revisa aparte; el script build pasó a ser tsc && tsc -p tsconfig.sw.json && vite build.

El evento sync no está en los tipos

Los tipos estándar de TypeScript no lo traen; se declara a mano la interfaz mínima (tag y lastChance).

src/db.ts (cola)
/** Anota (o reinicia a «pendiente») la descarga de varios modelos. */
export function encolarDescargas(db: IDBDatabase, ids: string[]): Promise<void> {
  return new Promise((resolve, reject) => {
    const tx = db.transaction("descargas", "readwrite");
    const store = tx.objectStore("descargas");
    ids.forEach((modeloId) => store.put({ modeloId, estado: "pendiente" } satisfies Descarga));
    tx.oncomplete = () => resolve();
    tx.onerror = () => reject(tx.error);
  });
}

Leer la cola y marcar una descarga como lista

src/db.ts (cola)
export function obtenerDescargas(db: IDBDatabase): Promise<Descarga[]> {
  return new Promise((resolve, reject) => {
    const peticion = db.transaction("descargas", "readonly").objectStore("descargas").getAll();
    peticion.onsuccess = () => resolve(peticion.result as Descarga[]);
    peticion.onerror = () => reject(peticion.error);
  });
}
src/db.ts (cola)
export function marcarDescargaLista(db: IDBDatabase, modeloId: string): Promise<void> {
  return new Promise((resolve, reject) => {
    const tx = db.transaction("descargas", "readwrite");
    tx.objectStore("descargas").put({ modeloId, estado: "listo" } satisfies Descarga);
    tx.oncomplete = () => resolve();
    tx.onerror = () => reject(tx.error);
  });
}

Evento sync · 6.4

Avisos con criterio: lastChance y la regla

La mayor diferencia con el Gestor está en el catch. Un fallo de sincronización es silencioso por defecto: el navegador reintenta sin que nadie lo sepa, y si deja de reintentar, el usuario nunca se entera de que su descarga no terminó.

El evento trae lastChance, que vale true en el último intento. Ahí —y solo ahí— se muestra «No se pudo completar la descarga». Antes de eso, notificar cada fallo sería ruido. Y se vuelve a lanzar el error, para que el navegador sepa que sí falló.

El resto sigue la regla de la Sesión 26:

  • Durante la descarga se mandan mensajes de progreso a las ventanas abiertas (la página pinta la barra).
  • La notificación del sistema solo sale si ninguna ventana está visible.
  • La ruta para /modelos/ primero busca en la caché modelos-3d y, si no está, va a la red: una ficha descargada se sirve aunque no haya conexión, y una no descargada sigue funcionando en línea.

Avisos de ciclo de vida de la PWA

Además, tres avisos de ciclo de vida de la PWA:

«La app ya funciona sin conexión»

registerSW ofrece el callback onOfflineReady, que se dispara cuando el precaché quedó completo por primera vez. Se muestra en pantalla; la notificación del sistema solo si la página no está visible.

«Atlas 3D instalado»

El evento appinstalled de la ventana. Aquí sí tiene sentido una notificación: el usuario acaba de pasar a otra ventana.

Abrir una ficha desde la notificación

El aviso lleva data.url = "/?modelo=ID"; al cargar, la página lee ese parámetro y resalta la tarjeta correspondiente.

Límites honestos de esta prueba

Límites honestos de esta prueba:
  • (1) El evento sync se disparó a mano con ServiceWorker.dispatchSyncEvent en los escenarios de fallo; en el escenario normal Chromium lo disparó solo al registrar, porque había red.
  • (2) El 404 se provocó renombrando una ficha dentro de dist/; no se cortó la red de un dispositivo.
  • (3) El clic en la notificación se simuló despachando un NotificationEvent dentro del SW.
  • (4) appinstalled se disparó como evento sintético: no se instaló la app de verdad.
  • (5) No hay push porque no hay servidor, y no se probó en teléfono real ni en iOS.
  • (6) Chromium sin pantalla siempre ve la página «visible»; la rama «hay ventana visible» se comprobó con la página abierta, y la rama «no hay ventana» cerrando la página y despachando el evento desde otra pestaña.

Resumen y próxima sesión

  • Lo conceptual de avisos, push y Background Sync se estudió en la Sesión 26; hoy se aplica a un proyecto sin servidor y empaquetado por Vite.
  • Sin servidor no hay push: se aplican notificaciones locales y Background Sync, este último invertido (descargar en vez de enviar).
  • strategies: "injectManifest" deja el SW en src/sw.ts; globIgnores: ["modelos/**"] evita que las fichas entren al precaché; skipWaiting() y clientsClaim() pasan a ser responsabilidad propia.
  • Como Vite empaqueta el SW, la función de descarga se escribe una sola vez y la comparten el SW y la página.
  • El fallo de un sync es silencioso: lastChance es el momento de avisar; la notificación del sistema se reserva para cuando no hay ventana visible.
  • Verificado en Chromium: cola, progreso, reintento parcial, uso con el servidor apagado, planes B. No verificado: push real (no existe en el Atlas), instalación real, teléfono, iOS.
Próxima sesión — Sesión 38: Realidad aumentada con WebXR (1/2). Detección de soporte y arranque de una sesión immersive-ar.
