SECCIÓN 01

El sw.js del Atlas 3D, enrutado por tipo de recurso

Cache First para íconos, Network First para un futuro /api/, Stale-While-Revalidate para el shell.

url.pathnamecacheFirst · networkFirst · staleWhileRevalidate
Enrutamiento · 1.1

Enrutar por url.pathname dentro de fetch

public/sw.js
self.addEventListener('fetch', event => {
  const url = new URL(event.request.url);

  if (url.pathname.startsWith('/iconos/')) {
    // Íconos y, más adelante, modelos .glb: inmutables → Cache First
    event.respondWith(cacheFirst(event.request));
  } else if (url.pathname.startsWith('/api/')) {
    // Futuro catálogo de modelos: debe verse al día → Network First
    event.respondWith(networkFirst(event.request));
  } else {
    // Shell (HTML, manifest): rápido, y se actualiza solo → Stale-While-Revalidate
    event.respondWith(staleWhileRevalidate(event.request));
  }
});
Las tres funciones son exactamente las de la Sesión 21, sin ningún cambio — lo único nuevo es la condición que decide cuál usar.
Enrutamiento · 1.2

Una rama que todavía no tiene ruta real detrás

El Atlas 3D todavía no tiene una ruta /api/ ni modelos .glb reales, pero ya tiene dos tipos de recurso claramente distintos: los íconos del manifest (binarios, inmutables) y el shell HTML/JS que Vite sirve.

La rama /api/ no tiene todavía ninguna ruta real detrás: queda ahí preparada para cuando el catálogo de modelos exista — exactamente como hizo la Sesión 21 con el Gestor de tareas.
SECCIÓN 02

Por qué esto no es lo mismo que "el visor funciona sin conexión"

Aplicar bien las 5 estrategias no resuelve el problema abierto desde la Sesión 29.

Estrategia correcta ≠ offline real
La aclaración honesta · 2.1

Qué resuelve el enrutamiento de hoy — y qué no

Aplicar correctamente las 5 estrategias — y el sw.js de la sección 1 sí las aplica correctamente — resuelve el problema de qué estrategia usa cada recurso cacheado.

No resuelve el problema, todavía abierto desde la Sesión 29, de que el propio Service Worker no logra interceptar ni /src/main.ts ni /@vite/client en modo desarrollo, ni el nombre con hash del bundle en producción (assets/index-BXm8pqCz.js, distinto en cada build).

Ese problema no es de estrategia: es de qué rutas exactas puede conocer de antemano el sw.js — y una lista de estrategias perfectamente elegidas no ayuda si la ruta que hay que cachear cambia de nombre en cada compilación.
La aclaración honesta · 2.2

Dos afirmaciones que suenan parecido, y no lo son

Cierto, desde hoy

"Cada recurso usa la estrategia correcta"

Los íconos vienen de Cache First, el shell de Stale-While-Revalidate, y la rama /api/ queda lista para Network First. Esto es sobre cómo se cachea — y hoy sí se hace bien.

Todavía falso

"La aplicación funciona sin conexión de verdad"

El sw.js no puede cachear de antemano /src/main.ts ni /@vite/client (desarrollo), ni un bundle con hash que cambia en cada build (producción). Esto es sobre qué se puede cachear — y eso sigue abierto.

Eso último es exactamente lo que Workbox resuelve, generando la lista de precaché en cada build en vez de escribirla a mano. Eso es la Sesión 34.
La aclaración honesta · 2.3

Lo que sí puedes verificar hoy, honestamente

Con npm run dev detenido y sirviendo solo los archivos estáticos de public/ (shell mínimo, manifest, íconos), el enrutamiento por tipo de recurso de la sección 1 funciona exactamente como se describe, estrategia por estrategia.

La limitación es específica de las rutas que Vite genera dinámicamente, no del enrutamiento en sí. No es un error de tu código — es la misma razón, documentada desde la Sesión 29, por la que un proyecto con empaquetador genera su lista de precaché automáticamente en vez de escribirla a mano.
