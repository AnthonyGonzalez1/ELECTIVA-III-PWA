Caché de modelos 3D (3/3)

Network First y Stale-While-Revalidate, y las 5 estrategias combinadas por tipo de recurso en el Atlas 3D — con una aclaración honesta sobre qué significa, y qué no, "funcionar sin conexión" en este proyecto todavía.

Objetivos de aprendizaje

  • ✓Aplicar Network First y Stale-While-Revalidate al sw.js del Atlas 3D.
  • ✓Combinar las 5 estrategias en el mismo Service Worker, enrutando por tipo de recurso.
  • ✓Distinguir "el Service Worker aplica la estrategia correcta a cada recurso" de "la aplicación funciona sin conexión de verdad" — no son lo mismo en un proyecto con Vite.
  • ✓Verificar en DevTools qué estrategia respondió cada petición del Atlas 3D.

Recursos de esta sesión

  • Descargar .zipCheckpoint — cierre de la Sesión 31. El sw.js ya responde con cacheFirst() para todo. Hoy dejamos de aplicar una sola estrategia a todo, y enrutamos varias según el tipo de recurso.

1Esto ya lo viste a fondo en la Sesión 21

Network First, Stale-While-Revalidate, la comparación completa de las 5 estrategias y el patrón de enrutar por path dentro de fetch ya los estudiaste con calma en la Sesión 21, sobre el Gestor de tareas. No repetimos nada de esa teoría aquí: si el porqué de alguna estrategia no te suena, vuelve primero a esa guía.

Lo que sí toca hoy es distinto: aplicar el mismo patrón de enrutamiento al sw.js real del Atlas 3D, que hasta la Sesión 31 solo usaba cacheFirst() para absolutamente todo.

2El sw.js del Atlas 3D, enrutado por tipo de recurso

El Atlas 3D todavía no tiene una ruta /api/ ni modelos .glb reales, pero ya tiene dos tipos de recurso claramente distintos: los íconos del manifest (binarios, inmutables) y el shell HTML/JS que Vite sirve. Eso alcanza para un enrutamiento real con dos estrategias, y para dejar preparado el tercer caso (una futura ruta de datos del catálogo) con Network First, exactamente como hizo la Sesión 21 con el Gestor de tareas:

public/sw.js
self.addEventListener('fetch', event => {
  const url = new URL(event.request.url);

  if (url.pathname.startsWith('/iconos/')) {
    // Íconos y, más adelante, modelos .glb: inmutables → Cache First
    event.respondWith(cacheFirst(event.request));
  } else if (url.pathname.startsWith('/api/')) {
    // Futuro catálogo de modelos: debe verse al día → Network First
    event.respondWith(networkFirst(event.request));
  } else {
    // Shell (HTML, manifest): rápido, y se actualiza solo → Stale-While-Revalidate
    event.respondWith(staleWhileRevalidate(event.request));
  }
});

Las tres funciones (cacheFirst, networkFirst, staleWhileRevalidate) son exactamente las de la Sesión 21, sin ningún cambio — lo único nuevo es la condición que decide cuál usar según url.pathname. La rama /api/ no tiene todavía ninguna ruta real detrás: queda ahí preparada para cuando el catálogo de modelos exista.

3Por qué esto no es lo mismo que "el visor funciona sin conexión"

Aplicar correctamente las 5 estrategias — y el sw.js de la sección 2 sí las aplica correctamente — resuelve el problema de qué estrategia usa cada recurso cacheado. No resuelve el problema, todavía abierto desde la Sesión 29, de que el propio Service Worker no logra interceptar ni /src/main.ts ni /@vite/client en modo desarrollo, ni el nombre con hash del bundle en producción (assets/index-BXm8pqCz.js, distinto en cada build). Ese problema no es de estrategia: es de qué rutas exactas puede conocer de antemano el sw.js, y una lista de estrategias perfectamente elegidas no ayuda si la ruta que hay que cachear cambia de nombre en cada compilación.

La distinción que importa hoy: "cada recurso usa la estrategia correcta" (cierto, desde hoy) no es lo mismo que "la aplicación funciona sin conexión de verdad" (todavía falso, para el bundle real de producción). Ambas cosas suenan parecido, pero la primera es sobre cómo se cachea, y la segunda es sobre qué se puede cachear — y eso último es exactamente lo que Workbox resuelve, generando la lista de precaché en cada build en vez de escribirla a mano. Eso es la Sesión 34.

Lo que sí puedes verificar hoy, honestamente: con npm run dev detenido y sirviendo solo los archivos estáticos de public/ (shell mínimo, manifest, íconos), el enrutamiento por tipo de recurso de la sección 2 funciona exactamente como se describe, estrategia por estrategia. La limitación es específica de las rutas que Vite genera dinámicamente, no del enrutamiento en sí.

Resumen de la sesión

  • Network First, Stale-While-Revalidate y el patrón de enrutar por path ya se estudiaron en la Sesión 21 — hoy solo se aplican al Atlas 3D.
  • El sw.js del Atlas 3D ahora enruta por tipo de recurso: Cache First para íconos, Stale-While-Revalidate para el shell, Network First preparado para un futuro /api/.
  • Aplicar bien las 5 estrategias no es lo mismo que "funcionar sin conexión de verdad": el sw.js no puede cachear de antemano rutas que Vite genera con nombre distinto en cada build.
  • Esa limitación —abierta desde la Sesión 29— se resuelve generando la lista de precaché automáticamente, en vez de escribirla a mano: eso es exactamente lo que hace Workbox, en la Sesión 34.
