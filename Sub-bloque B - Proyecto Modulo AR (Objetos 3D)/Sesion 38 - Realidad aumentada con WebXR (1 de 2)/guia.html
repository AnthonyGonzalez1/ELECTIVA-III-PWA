Realidad aumentada con WebXR (1/2)

Hasta ahora el cubo del Atlas solo se dibujaba encima del video de la cámara. Hoy el Atlas abre una sesión de realidad aumentada de verdad con WebXR: el sistema muestra la cámara y sigue el movimiento del teléfono, y nuestra página dibuja el cubo en ese espacio. Aprendemos a preguntar si se puede, a pedir la sesión sin invadir, a entrar y salir sin dejar la app rota — y a ser honestos con lo que todavía no es: el cubo flota, no se apoya en nada.

Objetivos de aprendizaje

  • ✓Distinguir una cámara de fondo (Sesión 36) de una sesión WebXR immersive-ar: quién dibuja la cámara, quién calcula el movimiento y qué recibe la página.
  • ✓Detectar con honestidad si un dispositivo puede abrir realidad aumentada, separando cuatro situaciones distintas (sin HTTPS, sin WebXR, sin AR, disponible).
  • ✓Pedir la sesión dentro de un clic, con requiredFeatures, optionalFeatures y un DOM overlay, y cerrarla devolviendo el visor al estado anterior.
  • ✓Conectar Three.js al bucle de la sesión XR y razonar en metros: tamaño y posición del objeto en el espacio local.
  • ✓Publicar el Atlas en una subruta de GitHub Pages sin romper rutas (BASE_URL) y verlo en un teléfono con ARCore.

1Lo que hicimos en la Sesión 36 no era realidad aumentada

En la Sesión 36 pusimos el video de la cámara detrás del canvas de Three.js. Se ve parecido a la realidad aumentada, pero el cubo solo está dibujado encima de una imagen: si mueves el teléfono, el cubo se queda pegado a la pantalla mientras el mundo se mueve por detrás. Para que el objeto parezca estar en el cuarto, alguien tiene que calcular, en cada fotograma, dónde está el teléfono en el espacio y mover la cámara virtual en consecuencia. Eso es lo que hace WebXR.

WebXR Device API es el estándar del navegador para realidad virtual y aumentada. Hoy usamos solo uno de sus modos, immersive-ar: la sesión ocupa toda la pantalla, el navegador (con ayuda del sistema, que en Android es ARCore) muestra la cámara real y sigue la posición del teléfono, y la página dibuja gráficos 3D sobre esa imagen. La diferencia práctica con la Sesión 36 es de quién hace qué:

Cámara de fondo (Sesión 36)Sesión immersive-ar (hoy)
¿Quién muestra la cámara?La página, con un <video> y getUserMediaEl navegador y el sistema; la página no recibe los píxeles de la cámara
¿Quién sigue el movimiento?Nadie (en la 35 se usó la orientación, sin posición)El sistema: posición y orientación del teléfono en cada fotograma
¿Dónde queda el cubo?Pegado a la pantallaEn un punto del espacio (aunque todavía no sobre una superficie real)
¿Qué ve el usuario?Un elemento más de la páginaUna experiencia de pantalla completa que el usuario inicia y puede cerrar
¿Dónde funciona?Casi cualquier navegador con cámaraPocos: hoy, esencialmente Chrome y navegadores basados en Chromium en Android con ARCore
La última fila resume la tabla de compatibilidad de caniuse.com consultada para esta sesión (Chrome en Android y Edge de escritorio: soporte parcial; Safari en iOS: sin soporte; Firefox: desactivado por defecto). El soporte cambia con las versiones: revisa la tabla vigente antes de prometerle AR a nadie.
Dos consecuencias que condicionan el diseño. (1) Como el navegador toma la cámara para la sesión AR, la cámara de fondo de la Sesión 36 y la sesión AR no pueden convivir: hoy apagamos una antes de abrir la otra. (2) Como en iPhone no hay AR por WebXR, el visor 3D con sensores y cámara de fondo sigue siendo la experiencia «principal» para esos usuarios; la AR es una mejora que se ofrece donde existe. Esta es la misma lógica de mejora progresiva de todo el curso.

2Antes de ofrecer el botón: ¿se puede?

La pregunta «¿tiene este navegador navigator.xr?» no alcanza. Hay cuatro respuestas distintas y cada una merece un mensaje distinto, porque le dicen al usuario qué hacer (o que no puede hacer nada). isSessionSupported("immersive-ar") consulta si el dispositivo puede abrir ese modo; no pide permiso ni abre nada, así que se puede llamar al cargar la página.

src/xr.ts (detección)
/** Resultado de preguntar «¿puedo usar AR aquí?». */
export type SoporteAR = "disponible" | "contexto-inseguro" | "sin-webxr" | "sin-ar";

/** Estado de soporte y, además, las comprobaciones una por una (para mostrarlas en pantalla). */
export async function diagnosticarAR(): Promise<{ estado: SoporteAR; lineas: string[] }> {
  const lineas: string[] = [];
  const seguro = window.isSecureContext;
  lineas.push(`Contexto seguro (HTTPS o localhost): ${seguro ? "sí" : "NO"}`);
  if (!seguro) return { estado: "contexto-inseguro", lineas };

  lineas.push(`navigator.xr: ${navigator.xr ? "presente" : "AUSENTE"}`);
  if (!navigator.xr) return { estado: "sin-webxr", lineas };

  try {
    // Responde si el DISPOSITIVO puede abrir ese modo; no pide permiso ni abre nada.
    const ok = await navigator.xr.isSessionSupported("immersive-ar");
    lineas.push(`isSessionSupported("immersive-ar"): ${ok}`);
    return { estado: ok ? "disponible" : "sin-ar", lineas };
  } catch (err) {
    lineas.push(`isSessionSupported("immersive-ar") lanzó: ${err instanceof Error ? err.name : String(err)}`);
    return { estado: "sin-ar", lineas };
  }
}

El orden de las comprobaciones importa: primero el contexto seguro (WebXR solo existe en HTTPS o localhost), luego la existencia de navigator.xr, y al final la pregunta por el modo. La función no devuelve solo el veredicto: guarda en lineas el resultado de cada comprobación, para poder mostrárselo a quien no logre activar el botón (lo verás en la sección 6). El try/catch existe porque isSessionSupported puede rechazar su promesa; si eso ocurre, lo tratamos como «sin AR» en vez de romper la página. Los mensajes viven en una función aparte, con un switch que cubre los cuatro casos:

src/xr.ts (mensajes)
export function mensajeSoporteAR(estado: SoporteAR): string {
  switch (estado) {
    case "disponible":
      return "Este dispositivo puede abrir una sesión de realidad aumentada.";
    case "contexto-inseguro":
      return "La realidad aumentada exige HTTPS o localhost.";
    case "sin-webxr":
      return "Este navegador no ofrece WebXR (por ejemplo, Safari en iPhone o Firefox). El visor 3D sigue funcionando.";
    case "sin-ar":
      return "Este dispositivo no admite realidad aumentada en el navegador (por ejemplo, un computador de escritorio sin el emulador activado).";
  }
}

En la página, el botón nace deshabilitado y solo se habilita si la respuesta es «disponible». Sea cual sea el resultado, la línea de estado le dice al usuario por qué, y un pequeño diagnóstico muestra las tres comprobaciones. La pregunta se repite al pulsar «Comprobar de nuevo» y cuando el navegador dispara devicechange (cambió el dispositivo XR), porque el soporte puede aparecer después de cargar la página, por ejemplo al activar un emulador:

src/main.ts (soporte al cargar)
const diagAR = document.querySelector<HTMLElement>("#diag-ar")!;
const detallesAR = document.querySelector<HTMLDetailsElement>(".diag-ar")!;
const btnRecomprobar = document.querySelector<HTMLButtonElement>("#btn-recomprobar")!;

// ¿Se puede? El botón solo se habilita si la respuesta es «sí». Se pregunta al
// cargar, al pulsar «Comprobar de nuevo» y cuando el navegador avisa de que
// cambió el dispositivo XR (así funciona también si activas el emulador después).
async function comprobarAR(): Promise<void> {
  const { estado, lineas } = await diagnosticarAR();
  estadoAR.textContent = mensajeSoporteAR(estado);
  diagAR.textContent = lineas.join("\n");
  if (!sesionAR) btnAR.disabled = estado !== "disponible";
  // Si no se puede, el diagnóstico se muestra abierto para ver qué comprobación falló.
  detallesAR.open = estado !== "disponible";
}
void comprobarAR();
btnRecomprobar.addEventListener("click", () => void comprobarAR());
navigator.xr?.addEventListener("devicechange", () => void comprobarAR());

3Pedir la sesión: gesto del usuario, funciones requeridas y opcionales

navigator.xr.requestSession(modo, opciones) devuelve una promesa con un objeto XRSession. Tres reglas que conviene saber antes de leer el código:

  • Se pide dentro de un clic. Entrar a una experiencia inmersiva es una acción que el usuario debe iniciar: según la especificación de WebXR, sin una activación reciente del usuario (un toque o un clic) la petición se rechaza con SecurityError. Por eso el código no abre la sesión al cargar la página: lo hace el manejador del botón.
  • requiredFeatures hace fallar; optionalFeatures no. Si falta alguna función requerida, la promesa se rechaza con NotSupportedError. Las opcionales se conceden si se puede y se ignoran si no, y la página debe seguir funcionando en ambos casos.
  • Los errores son parte del diseño. NotSupportedError y SecurityError son los dos que vale la pena explicar al usuario; cualquier otro se resume en un mensaje genérico.
src/xr.ts (pedir la sesión)
/**
 * Pide la sesión AR. DEBE llamarse desde el manejador de un clic: sin gesto del
 * usuario, el navegador la rechaza con SecurityError.
 */
export function pedirSesionAR(overlay: HTMLElement | null): Promise<XRSession> {
  const opciones: XRSessionInit & { domOverlay?: { root: Element } } = {
    requiredFeatures: ["local"], // el origen (0,0,0) es donde está el usuario al empezar
    optionalFeatures: ["dom-overlay"], // si existe, el botón «Salir» se dibuja sobre la cámara
  };
  if (overlay) opciones.domOverlay = { root: overlay };
  return navigator.xr!.requestSession("immersive-ar", opciones);
}

Las dos funciones elegidas, y qué significan:

  • "local" (requerida). Define el espacio de referencia: un sistema de coordenadas cuyo origen queda cerca de donde está el teléfono al empezar la sesión. Las unidades son metros, y el sentido «hacia adelante» es el eje −Z. Un objeto en (0, 0, −1.5) aparece a metro y medio frente a ti. Es el espacio más simple; la Sesión 39 agregará hit-test para ubicar superficies reales.
  • "dom-overlay" (opcional). En AR de teléfono la pantalla completa es la cámara, así que un botón normal de tu página no se vería. Esta función le permite al navegador dibujar un elemento HTML tuyo (domOverlay.root) encima de la cámara. Lo usamos para el botón «Salir de AR». Es opcional porque la AR debe poder abrirse aunque el navegador no la ofrezca.

El elemento overlay vive en el HTML, oculto por defecto, y el CSS lo muestra solo mientras dura la sesión, con la pseudoclase :xr-overlay. Según la especificación de DOM Overlays, el navegador estira ese elemento por toda la pantalla con fondo transparente, así que el CSS solo decide cómo acomodar lo de adentro:

index.html y style.css (overlay)
    <div id="xr-overlay" class="xr-overlay">
      <p id="xr-estado">Sesión de realidad aumentada activa</p>
      <button type="button" id="btn-salir-ar">Salir de AR</button>
    </div>
src/style.css (overlay)
.xr-overlay { display: none; }
/* Mientras dura la sesión, el navegador estira este elemento sobre toda la pantalla
   (fondo transparente). Solo hay que decir cómo acomodar lo de adentro. */
.xr-overlay:xr-overlay { display: flex; flex-direction: column; justify-content: flex-end; align-items: center; gap: .6em; padding-bottom: 1.2em; box-sizing: border-box; }
.xr-overlay p { margin: 0; background: rgba(11, 18, 32, .75); color: #e8e2cf; padding: .4em .8em; border-radius: 8px; font-size: .9em; }
.xr-overlay button { background: #ffcc29; color: #0b1220; border: 0; border-radius: 8px; padding: .7em 1.2em; font-weight: 700; cursor: pointer; }
No des por hecho que el botón aparecerá. Como dom-overlay es opcional, el navegador puede no concederlo. La sesión expone domOverlayState (con un campo type) solo si lo concedió; el código lo comprueba y, si falta, le avisa al usuario que debe salir con el mecanismo de salida del sistema. Un emulador sin DOM Overlay ejercita la rama «no concedido»; la rama «concedido» se simula en la prueba. En Chrome para Android, con ARCore, el navegador sí lo concede: la figura de la sección 9 muestra el botón «Salir de AR» dibujado sobre la cámara.

4Three.js dentro de la sesión: el bucle, la escala y el origen

Three.js trae soporte WebXR en renderer.xr. Conectar el visor a la sesión exige cuatro decisiones, todas visibles en el código:

  1. El reloj cambia. Con requestAnimationFrame el navegador llama a tu función al ritmo de la pantalla; en una sesión XR el ritmo y las poses los marca la sesión. Three.js lo resuelve con renderer.setAnimationLoop(función). Por eso, al entrar a AR se cancela el requestAnimationFrame del visor normal, y al salir se vuelve a arrancar.
  2. El fondo desaparece. escena.background = null: la imagen de la cámara la pone el navegador detrás de tu canvas, así que no hay que pintar nada. El renderer ya se creó con alpha: true en la Sesión 36, que es lo que permite esa transparencia.
  3. Los números son metros. El cubo de prueba mide 1,6 unidades. En pantalla normal eso es solo «un cubo grande»; en AR sería un cubo de 1,6 metros (más alto que un niño) a la altura de tu cara. Se escala a 0,25 (unos 40 cm) y se aleja 1,5 m.
  4. Hay que dejar todo como estaba. El visor guarda posición, escala y fondo antes de entrar, y los restaura cuando la sesión termina, sea por el botón «Salir», por el sistema o por un error.
src/visor.ts (entrarEnAR)
  async function entrarEnAR(sesion: XRSession, alTerminar: () => void) {
    cancelAnimationFrame(animacion); // en AR NO manda requestAnimationFrame: manda el reloj del visor XR
    renderer.xr.enabled = true;
    renderer.xr.setReferenceSpaceType("local");
    await renderer.xr.setSession(sesion);
    sesionAR = sesion;

    const fondoPrevio = escena.background;
    escena.background = null; // la cámara real es el fondo: no se pinta nada detrás
    controles.enabled = false;
    // Un cubo de 1,6 m sería gigante: se reduce a ~40 cm y se pone 1,5 m delante,
    // un poco por debajo de la vista. En el espacio «local» el origen es el usuario.
    const posicionPrevia = grupo.position.clone();
    const escalaPrevia = grupo.scale.clone();
    grupo.position.set(0, -0.2, -1.5);
    grupo.scale.setScalar(0.25);

    renderer.setAnimationLoop(() => {
      grupo.rotation.y += 0.01; // prueba de vida: el cubo gira solo
      renderer.render(escena, camara);
    });

    sesion.addEventListener(
      "end",
      () => {
        renderer.setAnimationLoop(null);
        renderer.xr.enabled = false;
        sesionAR = null;
        escena.background = fondoPrevio;
        controles.enabled = !porSensores;
        grupo.position.copy(posicionPrevia);
        grupo.scale.copy(escalaPrevia);
        grupo.rotation.set(0, 0, 0);
        ajustarTamano(); // el visor XR cambió el tamaño del canvas
        bucle(); // vuelve el requestAnimationFrame normal
        alTerminar();
      },
      { once: true }
    );
  }

Detalles finos: renderer.xr.setSession(sesion) es asíncrona (devuelve una promesa), por eso se espera con await antes de tocar la escena. El cubo gira solo (rotation.y += 0.01) porque, sin superficie real todavía, es la forma más rápida de saber que el bucle XR está vivo. Y el listener de end se registra con { once: true }: la sesión termina una sola vez, y así el listener no se acumula si el usuario abre y cierra AR varias veces.

Ojo con el origen «local». El cubo queda en una posición fija respecto a donde estaba el teléfono al empezar la sesión. Si caminas hacia él, te acercas; si miras a otro lado, sale del encuadre. Pero no está apoyado en el piso ni en una mesa: el sistema aún no le dijo a la página dónde hay superficies. Eso es hit-test, y es el tema de la Sesión 39. Hoy es «un cubo flotando a metro y medio», no «un cubo sobre tu escritorio».

5El botón «Ver en AR»: ordenar lo que hay antes de entrar

El visor ya tiene tres formas de «mover» el cubo (ratón o dedo, sensores, cámara de fondo). Al abrir la sesión AR hay que decidir qué pasa con cada una, y la respuesta es: se apagan las que compiten. La cámara de fondo, porque la AR necesita la cámara; los sensores, porque la sesión XR ya entrega la orientación real del teléfono, y dos fuentes moviendo la misma cámara se estorban. El orden dentro del manejador es parte de la lógica:

src/main.ts (el botón)
btnAR.addEventListener("click", async () => {
  avisarVisor("");
  // La cámara del navegador y la sesión AR no pueden usarse a la vez: la AR
  // abre la cámara por su cuenta. Se apagan también los sensores de la Sesión 35.
  apagarCamara();
  apagarSensores();
  try {
    // La petición ocurre DENTRO del clic: es el «gesto del usuario» que exige WebXR.
    const sesion = await pedirSesionAR(overlayAR);
    sesionAR = sesion;
    btnAR.disabled = true;
    await visor.entrarEnAR(sesion, () => {
      sesionAR = null;
      btnAR.disabled = false;
      estadoAR.textContent = "La sesión de realidad aumentada terminó.";
    });
    // domOverlayState existe solo si el navegador concedió la función «dom-overlay».
    estadoAR.textContent = sesion.domOverlayState
      ? "Sesión de realidad aumentada activa. Usa «Salir de AR» sobre la cámara."
      : "Sesión de realidad aumentada activa. Este navegador no mostró el botón sobre la cámara: sal con el gesto de salida del sistema.";
  } catch (err) {
    sesionAR?.end().catch(() => {});
    sesionAR = null;
    btnAR.disabled = false;
    avisarVisor(describirErrorAR(err));
  }
});
  • La petición ocurre en el clic. Antes de ella solo hay llamadas síncronas (apagarCamara, apagarSensores), que no consumen el «gesto» del usuario.
  • El catch limpia todo. Si pedirSesionAR o entrarEnAR fallan, se cierra la sesión si quedó abierta, se rehabilita el botón y se explica el motivo con describirErrorAR. El visor 3D sigue disponible.
  • El callback de fin (segundo argumento de entrarEnAR) devuelve la página a su estado normal sin importar quién cerró la sesión.
  • «Salir de AR» solo llama a sesion.end(); la restauración la hace el mismo listener de end de siempre. Un único camino de salida es más fácil de razonar que tres.
src/main.ts (salir)
btnSalirAR.addEventListener("click", () => {
  void sesionAR?.end();
});

6Cómo probar WebXR sin un teléfono: un emulador

Un computador de escritorio no tiene sesiones AR. Para comprobar el código (no la experiencia) puedes usar un emulador de WebXR. Hay dos caminos y comparten tecnología: la extensión de Chrome Immersive Web Emulator, de Meta, para usarla a mano mientras desarrollas; y la librería IWER (Immersive Web Emulation Runtime), en la que se apoya la extensión, para escribir pruebas automáticas. Ambas reemplazan navigator.xr por una implementación simulada de un casco Meta Quest que acepta sesiones immersive-ar y entrega fotogramas.

Los pasos con la extensión (los nombres exactos de los controles cambian entre versiones, pero la lógica es siempre esta):

  1. Instálala desde la Chrome Web Store (busca «Immersive Web Emulator», de Meta) y fíjala en la barra de herramientas. No aparece en chrome://extensions hasta que la instales.
  2. Abre el Atlas en localhost:4173 y pulsa el icono de la extensión para activar la emulación en ese sitio: la extensión solo actúa en las páginas donde la activas, y recarga la página al hacerlo. Si no ves cambios, recarga.
  3. Abre las DevTools (F12) y busca la pestaña WebXR. Elige un dispositivo con realidad aumentada, como el Meta Quest 3; un casco que solo hace realidad virtual responde «no» a immersive-ar.
  4. Despliega «Diagnóstico de realidad aumentada» bajo el visor. Las tres líneas deben decir sí / presente / true. Si cambiaste algo después de cargar, pulsa «Comprobar de nuevo».

El diagnóstico te dice qué falló, línea por línea:

Línea del diagnósticoQué significaQué hacer

No aparece el diagnóstico ni el botón «Ver en AR»Estás ejecutando una versión anterior de la app.Usa el .zip «Versión terminada de esta sesión» y limpia los datos del sitio (sección 8).

La extensión no implementa DOM Overlay, así que con ella el botón «Salir de AR» no se dibuja sobre la cámara y la app muestra el mensaje «sal con el gesto de salida del sistema»: en el emulador, termina la sesión con sus propios controles. Es justo la rama que la sección 3 pedía no dar por hecha. Según las notas de las versiones de la extensión, hit-test y los anclajes (anchors) están soportados desde la 1.2, lo que será útil en la próxima sesión.

Un detalle que importa si usas IWER como librería: Chromium de escritorio ya define un navigator.xr propio (que responde «no» a todo), y IWER, por defecto, no lo reemplaza. Se instala con installRuntime({ forceInstall: true }); sin esa opción, el emulador parece no hacer nada y la página dice que no hay AR.

(1) IWER comprueba que el código usa bien la API, no que funcione en un teléfono con ARCore: para eso, la prueba en un teléfono Android (sección 9). (4) IWER no implementa DOM Overlay, así que domOverlayState vino vacío en el escenario D y se simuló en el F. (5) El requisito de gesto del usuario viene de la especificación; el emulador no lo exige. (6) El contexto «inseguro» se simula redefiniendo window.isSecureContext; para verlo de verdad, sirve la app con npm run preview -- --host y ábrela por la dirección IP del computador desde otro equipo. 9Verlo en tu teléfono: publicar en GitHub Pages

WebXR exige HTTPS, y el emulador no muestra la cámara real ni el seguimiento de movimiento. Para ver el cubo en tu teléfono (Android, con Chrome y ARCore) hay que publicar el Atlas en una dirección HTTPS. GitHub Pages lo hace gratis, directamente desde un repositorio.

La trampa de la subruta

Un repositorio llamado atlas-3d no se publica en usuario.github.io, sino en usuario.github.io/atlas-3d/: una subruta. En local, el Atlas vivía en la raíz, y varias rutas estaban escritas como "/iconos/icon-192.png". En GitHub Pages esa ruta apuntaría a usuario.github.io/iconos/…, que no existe: iconos rotos, un manifest que no se instala, un Service Worker que no intercepta lo que debe. La solución tiene tres piezas:

  • Vite conoce la ruta base. Se le pasa al compilar: npm run build -- --base=/atlas-3d/. Con eso reescribe las rutas del index.html y de los archivos generados. Sin --base, la base es / y todo sigue como antes.
  • El código no escribe rutas absolutas a mano. En su lugar usa import.meta.env.BASE_URL, que vale / en local y /atlas-3d/ publicado.
  • El manifest usa rutas relativas ("start_url": "./", "scope": "./", iconos como "iconos/icon-192.png"), que se resuelven respecto al propio manifest.
src/descargas.ts (ruta de una ficha)
// BASE_URL vale «/» en local y «/nombre-del-repo/» en GitHub Pages: nunca escribas rutas absolutas a mano.
export const urlDeModelo = (id: string) => `${import.meta.env.BASE_URL}modelos/${id}.json`;
src/sw.ts (ruta base en el Service Worker)
// Ruta base de la app: «/» en local, «/nombre-del-repo/» en GitHub Pages.
const BASE = import.meta.env.BASE_URL;

registerRoute(
  ({ url }) => url.pathname.startsWith(BASE + "iconos/"),

La misma regla vale para el Service Worker, las notificaciones (icono y destino al tocarlas) y las fichas de modelos: todo cuelga de BASE.

Publicar, paso a paso

Necesitas una cuenta de GitHub. El orden importa: primero se activa Pages con la fuente «GitHub Actions» y después se sube el proyecto.

  1. Crea el repositorio. En github.com pulsa New (o «Create a new repository»). Ponle un nombre sin espacios, por ejemplo atlas-3d (será la subruta), márcalo Public y créalo. No hace falta añadir README ni .gitignore.
  2. Activa Pages con la fuente «GitHub Actions». Dentro del repositorio: Settings → Pages → Build and deployment → Source, y elige GitHub Actions en la lista.
  3. No pulses «Configure». Al elegir esa fuente, GitHub te sugiere dos flujos, «GitHub Pages Jekyll» y «Static HTML», cada uno con un botón Configure. No uses ninguno: «Static HTML» publica los archivos del repositorio tal cual, sin compilar, y el Atlas necesita compilarse (TypeScript y Vite). El flujo que sí sirve, pages.yml, ya viene dentro del proyecto. En esta pantalla no hay nada más que configurar.
  1. Sube el proyecto. Descomprime pwa-ar-objetos3d-sesion38.zip en tu equipo. En la pestaña Code del repositorio vacío pulsa uploading an existing file (o Add file → Upload files), arrastra el contenido de la carpeta (src, public, .github, index.html, package.json…, no la carpeta que los contiene) y pulsa Commit changes. Si arrastras una carpeta de más (como node_modules o dist), no la subas: no deben estar en el repositorio.
  2. Comprueba que el flujo llegó. En la pestaña Code debe verse la carpeta .github, y dentro workflows/pages.yml. Si no aparece (algunos exploradores no arrastran carpetas ocultas): Add file → Create new file, escribe como nombre .github/workflows/pages.yml (cada «/» crea una carpeta), pega el contenido del archivo que aparece más abajo y pulsa Commit changes.
  3. Mira la compilación. Abre la pestaña Actions. Verás una ejecución llamada «Publicar en GitHub Pages»: punto amarillo, en curso; ✓ verde, terminada (suele tardar uno o dos minutos). Si la subida terminó antes de activar Pages, o no aparece ninguna ejecución, entra en «Publicar en GitHub Pages» en la columna izquierda, pulsa Run workflow y confirma con la rama main. Si la ejecución sale con ✗ roja, ábrela y lee el paso que falló.
  1. Abre tu página. Con la ejecución en verde, la dirección está en Settings → Pages («Your site is live at…») y tiene la forma https://tu-usuario.github.io/atlas-3d/.
  2. Pruébala en el teléfono. Ábrela en Chrome del teléfono. Despliega el «Diagnóstico de realidad aumentada»: debe decir sí / presente / true. Toca «Ver en AR», acepta el permiso de la cámara y apunta el teléfono a tu alrededor: el cubo debe estar a metro y medio, girando. Camina hacia él y rodéalo: es la diferencia con la cámara de fondo de la Sesión 36.
.github/workflows/pages.yml
name: Publicar en GitHub Pages

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: pages
  cancel-in-progress: true

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm install
      # --base le dice a Vite en qué subruta vivirá la app: /nombre-del-repo/
      - run: npm run build -- --base=/${{ github.event.repository.name }}/
      - uses: actions/upload-pages-artifact@v3
        with:
          path: dist

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - id: deployment
        uses: actions/deploy-pages@v4

Este es el flujo pages.yml que viene dentro del proyecto. Se ejecuta con cada subida a la rama main, o a mano con «Run workflow». Tiene dos trabajos: build instala dependencias, compila con --base=/${{ github.event.repository.name }}/ (el nombre del repositorio se toma solo) y sube la carpeta dist; deploy la publica en Pages. Si un día cambias el nombre del repositorio, no hay que tocar nada.

Resumen de la sesión

  • WebXR immersive-ar no es «cámara de fondo + 3D»: el sistema muestra la cámara y sigue el movimiento, y la página dibuja sobre esa imagen sin recibir los píxeles.
  • Se detecta con cuatro respuestas distintas (sin HTTPS, sin WebXR, sin AR, disponible) y un mensaje para cada una; el botón solo se habilita si la respuesta es «disponible».
  • La sesión se pide dentro de un clic, con local requerida y dom-overlay opcional; los errores se explican y el visor sigue funcionando.
  • En AR el bucle lo marca la sesión (setAnimationLoop), las unidades son metros y el eje −Z va hacia adelante; todo lo que se cambia al entrar se restaura al salir.
  • Un emulador comprueba el código (detección, petición, bucle, salida, reentrada y errores); la experiencia real (la cámara, la posición visual del cubo, el botón sobre la cámara, el gesto de usuario) solo se comprueba en un teléfono con ARCore.
  • Para ver AR de verdad hay que publicar con HTTPS: en GitHub Pages la app vive en una subruta, así que ninguna ruta se escribe a mano: se usa import.meta.env.BASE_URL, un manifest con rutas relativas y --base al compilar.
