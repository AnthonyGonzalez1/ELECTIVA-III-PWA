2¿Qué es un Service Worker? (repaso)

Esto ya lo viste en la Sesión 17 — un repaso breve basta. Un Service Worker es un bloque de código que la aplicación instala en el navegador, y que se ejecuta en función de eventos — no de la interacción directa del usuario con la página. Es, en esencia, un proxy programable entre la aplicación y la red [1]. El navegador exige tres requisitos para instalarlo, y los tres se cumplen igual en un proyecto Vite que en el Gestor de tareas:

  • Soporte del navegador: todos los navegadores modernos soportan la API de Service Workers.
  • Conexión segura: HTTPS en producción, o localhost durante el desarrollo — que es exactamente donde corre npm run dev.
  • Mismo origen: el script del Service Worker debe servirse desde el mismo servidor que la aplicación.

3Registrar el Service Worker en un proyecto Vite

La llamada de registro es la misma API que en la Sesión 17 — lo único que cambia es dónde vive cada pieza. En el Gestor de tareas el registro estaba en app.js, un script suelto cargado por <script>. En el Atlas 3D no hay un app.js: hay un único punto de entrada, src/main.ts, que Vite procesa y empaqueta. Ahí es donde agregamos el registro:

src/main.ts
// Registro del Service Worker — Sesión 28.
if ("serviceWorker" in navigator) {
  navigator.serviceWorker
    .register("/sw.js")
    .then((reg) => console.log("SW registrado:", reg.scope))
    .catch((err) => console.error("Error al registrar SW:", err));
}

La particularidad de hoy es esta: register("/sw.js") le pide al navegador un archivo en la raíz del sitio — pero src/ no se sirve tal cual, Vite lo procesa y lo empaqueta. Si el sw.js se pusiera junto al resto del código fuente, Vite lo transformaría (o ni siquiera lo copiaría a la build), y /sw.js respondería 404. La solución ya la conoces de la Sesión 27: todo lo que va en public/ se sirve exactamente como está, sin procesar, directamente desde la raíz — igual que el manifest.json y los íconos. El Service Worker no es la excepción, es el mismo caso:

public/ ├── sw.js // nuevo hoy — se sirve como /sw.js, sin procesar ├── manifest.json // de la Sesión 27 └── iconos/ src/ └── main.ts // agrega aquí el bloque de registro de arriba
Dato clave: esto funciona igual en npm run dev y después de npm run build — el servidor de desarrollo de Vite también sirve public/ tal cual desde la raíz, así que no hay sorpresas al pasar de desarrollo a producción [5].

4El ciclo de vida completo

El ciclo de vida no cambia por usar Vite: es exactamente el mismo que estudiaste en la Sesión 17, diseñado para el funcionamiento offline, las actualizaciones eficientes y el control de las solicitudes de red [2]. Repaso de sus seis fases:

1
"install" eventRegistro e instalación

navigator.serviceWorker.register() registra el archivo. Durante install, el Service Worker suele cachear los recursos esenciales. Si falla, no se activa.

2
waitingEspera

Permanece inactivo hasta que el Service Worker anterior deja de controlar las sesiones activas. Nunca hay más de uno activo al mismo tiempo.

3
"active" eventActivación

Una vez activado, asume el control de la aplicación, gestionando cachés y migrando datos si hace falta.

4
"fetch" eventInterceptación de solicitudes

Se dispara con cada petición de red. Hoy solo lo registramos y lo dejamos pasar tal cual — interceptar de verdad y responder desde caché es el tema completo de la Sesión 29.

5
"updatefound" eventActualización

El Service Worker se mantiene activo hasta que se registra una nueva versión, que el navegador instala y deja en espera hasta reemplazar a la anterior [3].

6
skipWaiting()Salto de espera (opcional)

Un Service Worker nuevo puede llamar a skipWaiting() para activarse de inmediato en vez de esperar a que se cierren todas las pestañas abiertas.

Las seis fases del ciclo de vida de un Service Worker — las mismas de la Sesión 17. Fuente: adaptado de J. Wargo, "Fig. 3: Ciclo de vida de un service worker" [2][3].

5Limitaciones de los Service Workers

Las mismas limitaciones de la Sesión 17 aplican tal cual al Atlas 3D — no dependen del framework ni de la herramienta de build [4]:

  • Solo se ejecutan si el navegador está abierto. En algunos dispositivos el navegador puede seguir corriendo en segundo plano, lo que mitiga parcialmente esta limitación.
  • No pueden manipular el DOM de la aplicación directamente — existen métodos de comunicación alternativos (mensajes) entre la página y el Service Worker.
  • Su implementación puede resultar compleja, a pesar de ofrecer un control muy detallado sobre caché y solicitudes de red.
  • Las PWA no están disponibles en tiendas como App Store o Google Play — deben instalarse directamente desde el navegador.
  • En iOS, las actualizaciones automáticas no son tan fluidas como en Android: el usuario suele tener que abrir la PWA manualmente para que se actualice el contenido.

6Caso real: el sw.js y el registro del Atlas 3D

Este es el sw.js mínimo que agregamos hoy al proyecto — la misma estructura de tres manejadores que en la Sesión 17, adaptada a los archivos reales del Atlas 3D. El manejador de fetch está presente porque el navegador lo exige para la instalabilidad, pero por ahora solo deja pasar la petición a la red tal cual — interceptar de verdad llega en la Sesión 29:

public/sw.js
const CACHE_NAME = 'atlas3d-v1';
const CORE_ASSETS = [
  '/',
  '/index.html',
  '/manifest.json',
];

self.addEventListener('install', event => {
  event.waitUntil(
    caches.open(CACHE_NAME).then(cache => cache.addAll(CORE_ASSETS))
  );
});

self.addEventListener('activate', event => {
  event.waitUntil(self.clients.claim());
});

self.addEventListener('fetch', event => {
  event.respondWith(fetch(event.request));
});

Nótalo bien: CORE_ASSETS ya llama a caches.open().addAll() dentro de install — pero eso todavía no significa que el Atlas 3D esté cacheando nada de verdad. Guardar esos tres archivos en caché durante la instalación es una precaución mínima y estándar del evento install; ninguna respuesta se sirve todavía desde esa caché, porque el manejador de fetch de arriba sigue yendo directo a la red. Cachear las rutas del visor y responder desde caché es, otra vez, el trabajo completo de la Sesión 29.

Y este es el fragmento que agregamos en src/main.ts para registrarlo — el mismo bloque de la sección 3:

src/main.ts (fragmento)
if ("serviceWorker" in navigator) {
  navigator.serviceWorker
    .register("/sw.js")
    .then((reg) => console.log("SW registrado:", reg.scope))
    .catch((err) => console.error("Error al registrar SW:", err));
}

Para verificarlo: F12 → pestaña Application → sección Service Workers. Chrome debe mostrar /sw.js registrado, con estado activated and is running. Y en la sección Manifest, la lista de "Installability" debería mostrar, por fin, los 5 criterios en verde — el mismo resultado que viste con el Gestor de tareas en la Sesión 17.

Resumen de la sesión

  • El Service Worker del Atlas 3D usa la misma API que viste en la Sesión 17: navigator.serviceWorker.register() y los tres requisitos de siempre (soporte, HTTPS/localhost, mismo origen).
  • La única diferencia real de un proyecto Vite: el sw.js debe vivir en public/ para servirse sin procesar en /sw.js, y el registro se agrega en src/main.ts, el punto de entrada del proyecto.
  • El ciclo de vida sigue teniendo seis fases: registro/instalación, espera, activación, fetch, actualización, y el salto opcional con skipWaiting().
  • El evento fetch de hoy solo deja pasar la petición a la red — interceptar de verdad y cachear rutas es el tema completo de la Sesión 29.
  • Con el Service Worker de hoy, el Atlas 3D cumple, por primera vez, los 5 criterios de instalabilidad — y la sesión cierra con un commit que lo deja registrado en tu propio repositorio.
