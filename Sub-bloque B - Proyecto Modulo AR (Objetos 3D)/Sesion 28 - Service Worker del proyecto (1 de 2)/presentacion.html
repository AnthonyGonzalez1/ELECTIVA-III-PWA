SECCIÓN 01

¿Qué es un Service Worker?

Repaso breve — esto ya lo viste completo en la Sesión 17.

Definición3 requisitos
¿Qué es un Service Worker? · 1.1

Un proxy programable, sin importar el proyecto

Un bloque de código que la app instala en el navegador, y que se ejecuta según eventos — no según la interacción del usuario. Los mismos tres requisitos de la Sesión 17 aplican igual en un proyecto Vite:

Soporte

El navegador debe soportar la API de Service Workers.

HTTPS

O localhost — justo donde corre npm run dev.

Mismo origen

El script debe venir del mismo servidor que la app.

SECCIÓN 02

Registrar el Service Worker en Vite

La misma llamada de la Sesión 17 — pero un archivo fuente no se sirve igual que un archivo suelto.

src/main.tspublic/sw.js
Registro · 2.1

Un archivo fuente, un archivo estático

src/main.ts
if ("serviceWorker" in navigator) {
  navigator.serviceWorker
    .register("/sw.js")
    .then((reg) => console.log("SW registrado:", reg.scope))
    .catch((err) => console.error("Error:", err));
}
public/sw.js // se sirve tal cual, sin procesar, en /sw.js src/main.ts // agrega aquí el bloque de registro
Dato clave: src/ lo procesa Vite; public/ se sirve tal cual desde la raíz — igual que el manifest de la Sesión 27. Por eso el Service Worker va en public/.
SECCIÓN 03

El ciclo de vida completo

Las mismas seis fases de la Sesión 17 — no cambian por usar Vite.

6 fases
Ciclo de vida · 3.1

Las seis fases (repaso)

1
"install"Registro e instalación

Se registra, y suele cachear los recursos esenciales. Si falla, no se activa.

2
waitingEspera

Inactivo hasta que el SW anterior deje de controlar las sesiones activas.

3
"active"Activación

Asume el control, gestiona cachés y migra datos si hace falta.

4
"fetch"Interceptación

Hoy solo lo registramos y dejamos pasar la petición — interceptar de verdad es la Sesión 29.

5
"updatefound"Actualización

Activo hasta que se registra una nueva versión, instalada y puesta en espera.

6
skipWaiting()Salto de espera

Un SW nuevo puede activarse de inmediato en vez de esperar.

SECCIÓN 04

Limitaciones de los Service Workers

Las mismas de siempre — no dependen del framework ni de la herramienta de build.

Limitaciones

Cinco límites que conviene conocer

  • Solo se ejecutan si el navegador está abierto (algunos dispositivos mitigan esto en segundo plano).
  • No pueden manipular el DOM directamente — se comunican con la página por mensajes.
  • Su implementación puede resultar compleja pese al control detallado que ofrecen.
  • Las PWA no están en App Store ni Google Play — se instalan desde el navegador.
  • En iOS, las actualizaciones no son tan fluidas como en Android.
SECCIÓN 05

Caso real: sw.js y registro del Atlas 3D

El archivo completo, y cómo verificar que quedó activo.

public/sw.js completo
Caso real · 5.1

El sw.js completo del Atlas 3D

public/sw.js
const CACHE_NAME = 'atlas3d-v1';
const CORE_ASSETS = ['/', '/index.html', '/manifest.json'];

self.addEventListener('install', event => {
  event.waitUntil(caches.open(CACHE_NAME).then(cache => cache.addAll(CORE_ASSETS)));
});

self.addEventListener('activate', event => {
  event.waitUntil(self.clients.claim());
});

self.addEventListener('fetch', event => {
  event.respondWith(fetch(event.request));
});
F12 → Application → Service Workers debe mostrar activated and is running. En Manifest → Installability, los 5 criterios por fin en verde — interceptar de verdad llega en la Sesión 29.

Cierre

Resumen de la lección

  • El Service Worker del Atlas 3D usa la misma API de la Sesión 17: navigator.serviceWorker.register() y los mismos 3 requisitos.
  • La diferencia real con Vite: sw.js vive en public/ (se sirve sin procesar), y se registra desde src/main.ts.
  • El ciclo de vida sigue teniendo 6 fases: instalación, espera, activación, fetch, actualización, skipWaiting.
  • El fetch de hoy solo deja pasar la petición — interceptar de verdad y cachear rutas es la Sesión 29.
  • Con esto, el Atlas 3D cumple, por primera vez, los 5 criterios de instalabilidad.
