APIs de dispositivo en el proyecto (1/2)

El Atlas 3D estrena su primer visor de Three.js y lo mueve con los sensores de orientación: inclinas el teléfono y el modelo gira, sin tocar la pantalla. Es el espejo de la Sesión 25, aplicado al proyecto — y, de paso, nos obliga a ser honestos con lo que el visor todavía no tiene.

Objetivos de aprendizaje

  • ✓Montar el primer visor de Three.js del Atlas 3D, con un modelo de prueba y control manual de respaldo.
  • ✓Convertir los ángulos absolutos de deviceorientation en una rotación relativa a una posición de referencia, con calibración.
  • ✓Suavizar el movimiento del modelo para filtrar el temblor del sensor, y apagar los sensores cuando no se usan.
  • ✓Verificar el resultado contra el build real, con sensores simulados, y declarar con honestidad qué todavía no es.

Recursos de esta sesión

  • Descargar .zipCheckpoint — cierre de la Sesión 34. El Atlas 3D con IndexedDB (Sesión 33) y el Service Worker generado por vite-plugin-pwa (Sesión 34). Todavía no tiene ningún visor 3D: hoy nace el primero.

1Esto ya lo viste a fondo en la Sesión 25

Qué miden deviceorientation y devicemotion, los rangos de alpha, beta y gamma, el permiso especial de iOS (requestPermission dentro de un clic), cómo detectar que un computador no tiene sensores reales y por qué se limita la frecuencia de lectura, está todo en la Sesión 25, aplicado al Gestor de Tareas. Aquí no se repite: en este proyecto se reutilizan las mismas ideas, escritas ahora en TypeScript en src/sensores.ts.

Lo que sí es nuevo hoy es la pregunta: en el Gestor, el sensor deshacía una eliminación; en el Atlas 3D, tiene que mover un modelo. Y para eso primero hace falta que exista algo que mover.

2Primero, un visor (y una advertencia honesta)

El Atlas 3D todavía no tiene visor. three está en package.json desde el andamiaje de la Sesión 27, pero hasta hoy ninguna línea lo importaba; y el catálogo de modelos reales (dominio, vista, controlador) es trabajo de sesiones futuras. Por eso el visor de hoy muestra un cubo de prueba, y la pantalla lo dice. Inventar un archivo .glb que no está en el proyecto sería peor que mostrar un cubo honesto.

El visor vive en su propio módulo, src/visor.ts, y expone una interfaz mínima — el resto de la app no sabe nada de Three.js:

src/visor.ts (fragmento)
export interface Visor {
  rotarHacia(rotX: number, rotY: number): void;   // rotación objetivo, en radianes
  controlPorSensores(activo: boolean): void;      // true: sensores; false: ratón/dedo
  rotacionActualGrados(): { x: number; y: number };
  destruir(): void;
}

export function crearVisor(contenedor: HTMLElement): Visor {
  const escena = new THREE.Scene();
  escena.background = new THREE.Color(0x0b1220);
  const camara = new THREE.PerspectiveCamera(50, 1, 0.1, 100);
  camara.position.set(0, 0, 4);
  const renderer = new THREE.WebGLRenderer({ antialias: true });
  contenedor.append(renderer.domElement);
  // ... luces, el cubo de prueba (BoxGeometry + MeshStandardMaterial) ...
  const controles = new OrbitControls(camara, renderer.domElement);  // respaldo sin sensores
  // ... bucle con requestAnimationFrame ...
}

OrbitControls (ratón o dedo) es la mejora progresiva de la Sesión 25 vista desde el otro lado: aquí el control manual es la base, y los sensores el atajo. Un portátil sin sensores sigue pudiendo girar el visor.

3De ángulos absolutos a rotación relativa

Nadie sostiene el teléfono exactamente a 0°. Si mapeas beta directo a la rotación del cubo, al activar los sensores el modelo salta de golpe a una posición rara. La solución es medir relativo a una referencia: la primera lectura que llega (o la que fije el usuario con "Calibrar") pasa a ser el cero. Dos ajustes más:

  • Conversión: los ángulos llegan en grados; Three.js rota en radianes (grados × π / 180).
  • Límite de ±90°: con ángulos de Euler (alpha/beta/gamma), cuando el teléfono se acerca a la vertical (beta cerca de ±90°) los ejes se vuelven inestables — el famoso bloqueo de cardán. Limitar el rango evita los saltos; una solución más robusta usaría cuaterniones, y hoy no la implementamos.
src/sensores.ts (fragmento)
export function iniciarControlOrientacion(
  onRotacion: (rotX: number, rotY: number) => void,
  intervaloMs = 33
): ControlOrientacion {
  let referencia: { beta: number; gamma: number } | null = null;
  let ultimaLectura: { beta: number; gamma: number } | null = null;
  let ultimoAviso = 0;

  const manejador = (e: DeviceOrientationEvent) => {
    if (e.beta === null || e.gamma === null) return;
    ultimaLectura = { beta: e.beta, gamma: e.gamma };
    if (!referencia) referencia = { ...ultimaLectura };       // la primera lectura = cero
    const ahora = performance.now();
    if (ahora - ultimoAviso < intervaloMs) return;            // ~30 avisos por segundo
    ultimoAviso = ahora;
    const dBeta  = limitar(e.beta  - referencia.beta,  -90, 90);
    const dGamma = limitar(e.gamma - referencia.gamma, -90, 90);
    onRotacion(dBeta * GRADOS_A_RAD, dGamma * GRADOS_A_RAD);   // beta → eje X, gamma → eje Y
  };

  window.addEventListener("deviceorientation", manejador);
  return {
    calibrar() {
      referencia = ultimaLectura ? { ...ultimaLectura } : null;
      onRotacion(0, 0);       // vuelve a neutro al instante
    },
    detener() { window.removeEventListener("deviceorientation", manejador); },
  };
}
Un error que apareció al verificar, y por qué está arreglado. La primera versión de calibrar() solo cambiaba la referencia, sin avisar al visor. Con un sensor simulado — que solo dispara un evento cuando su valor cambia — el modelo se quedaba en su posición vieja hasta la lectura siguiente. En un teléfono real no se nota (el sensor nunca está del todo quieto), pero un comportamiento que depende de que algo "se mueva solo" es frágil. Ahora calibrar() emite (0, 0) de inmediato.

4Suavizar: filtrar el temblor

Los sensores reales tiemblan, aunque tengas el teléfono quieto. Si el cubo copia cada lectura, vibra. El visor, en cambio, no salta a la rotación objetivo: en cada fotograma avanza un 15 % del camino que le falta (interpolación lineal). Es un filtro muy simple, y suficiente para que el movimiento se vea fluido:

src/visor.ts (fragmento)
function bucle() {
  animacion = requestAnimationFrame(bucle);
  if (porSensores) {
    grupo.rotation.x += (objetivoX - grupo.rotation.x) * 0.15;
    grupo.rotation.y += (objetivoY - grupo.rotation.y) * 0.15;
  }
  controles.update();
  renderer.render(escena, camara);
}

Un 0,15 es un punto de partida, no una verdad: más bajo es más suave pero con más retraso; más alto es más reactivo pero tiembla más. Ajustarlo con un teléfono en la mano es la actividad de hoy.

5Conectar todo en main.ts

El botón "📱 Rotar con el teléfono" sigue el mismo flujo de la Sesión 25: permiso dentro del clic, comprobación de sensores reales, mensaje claro en cada rama, y un segundo clic que apaga. La diferencia es que cuando los sensores se activan, visor.controlPorSensores(true) desactiva OrbitControls (dos controles peleando por el mismo modelo se ven fatal) y lo reactiva al apagar:

src/main.ts (fragmento)
btnOrientacion.addEventListener("click", async () => {
  if (control) { apagarSensores(); return; }          // segundo clic: volver al control manual
  const permiso = await pedirPermisoOrientacion();    // en iOS, dentro del clic
  if (permiso === "denied") {
    avisarVisor("Denegaste el acceso a los sensores. Sigue disponible el control con ratón o dedo.");
    return;
  }
  if (permiso === "no-soportado" || !(await hayOrientacionReal())) {
    avisarVisor("Este dispositivo no tiene sensores de orientación. Usa el ratón o el dedo para girar el visor.");
    return;
  }
  visor.controlPorSensores(true);
  control = iniciarControlOrientacion((x, y) => visor.rotarHacia(x, y));
  btnCalibrar.disabled = false;
});
Por qué dos mensajes de fallo distintos: "denegaste el acceso" (el usuario eligió no) y "no hay sensores" (el dispositivo no puede) son situaciones distintas, y el usuario necesita saber cuál es para reaccionar.

6Verificado contra el build real

Todo lo que sigue se ejecutó contra npm run build + npm run preview (no contra el servidor de desarrollo) en Chromium con WebGL por software, y sensores simulados vía protocolo de DevTools: una inclinación inicial de 20°, luego 50° (30° más), calibración, y luego 60° (10° más que la nueva referencia). Qué demuestra: (1) sin sensores, el visor lo detecta y recomienda ratón o dedo; (2) con sensores, la referencia es la primera lectura (rotación 0°) y una inclinación de +30° produce exactamente 30°; (3) tras calibrar, el cero pasa a ser la posición actual y +10° físicos dan 10°; (4) al apagar, el visor vuelve a neutro y el indicador se limpia; (5) con la conexión cortada, la página recarga con el visor montado — el Service Worker de la Sesión 34 sigue cumpliendo; (6) cero errores de página.

Un dato de ingeniería que apareció gratis: el precaché pasó de 25,40 KiB (Sesión 34) a unos 507 KiB. No es un error: es el peso de Three.js, que por fin se importa de verdad. Es el primer número real del costo de un visor 3D en una PWA — y una razón concreta para vigilar el tamaño del bundle en las próximas sesiones.

Lo que esta verificación NO es: una prueba con un teléfono real. Los sensores simulados no tienen ruido, y en un teléfono el suavizado de 0,15 y el límite de ±90° se sentirán distinto. Tampoco se probó el permiso de iOS (ver la Sesión 25, sección 2).

7Probar en un teléfono real

Los sensores solo existen en un teléfono y solo se entregan en contexto seguro. Ojo: npm run dev servido por la red local (http://192.168.x.x:5173) es HTTP, así que en el teléfono no habrá sensores. Usa alguno de los caminos de la Sesión 24, sección 9 (reenvío de puerto por USB, túnel HTTPS, o publicar en GitHub Pages). Y recuerda que el Service Worker solo existe en el build: para ver lo que ve el usuario, npm run build y npm run preview.

Resumen de la sesión

  • Los permisos, el caso de iOS y la detección de sensores reales ya se estudiaron en la Sesión 25; hoy se aplican en TypeScript, sin repetir la teoría.
  • El Atlas 3D no tenía visor: hoy nace uno, con un cubo de prueba explícitamente declarado (el catálogo real no existe todavía), y OrbitControls como respaldo sin sensores.
  • La rotación se calcula relativa a una referencia (primera lectura o calibración), convertida a radianes y limitada a ±90° para evitar inestabilidades de ángulos de Euler.
  • El modelo avanza un 15 % por fotograma hacia su objetivo, suavizando el temblor del sensor; apagar los sensores devuelve el visor al control manual.
  • Verificado contra el build real con sensores simulados: inclinación, calibración, apagado y recarga sin conexión; el precaché creció a unos 507 KiB por el peso de Three.js.
  • Pendiente de verificar en hardware real: ruido de sensores, la calibración fina del suavizado y la rama de iOS.
