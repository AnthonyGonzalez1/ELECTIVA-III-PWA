Antes de empezar

Esto ya lo viste a fondo en la Sesión 23

Qué es Workbox, sus módulos, la diferencia entre GenerateSW e InjectManifest, compatibilidad de navegadores, UX/UI y Lighthouse, ya lo estudiaste con calma en la Sesión 23, sobre el Gestor de Tareas. No repetimos nada de esa teoría aquí.

Lo que sí toca hoy es distinto, y es el motivo por el que esta sesión importa más que un simple "aplicarlo al proyecto": el Gestor de Tareas no tiene bundler, así que Workbox generó su sw.js leyendo archivos planos. El Atlas 3D sí tiene un bundler — Vite — y es exactamente ese bundler el que rompió el offline manual en la Sesión 29. Hoy vemos por qué Workbox integrado al build sí lo resuelve.
SECCIÓN 02

Recordando el problema exacto de la Sesión 29

Un sw.js manual no sobrevive a un bundler que renombra sus archivos en cada build.

CORE_ASSETS a manoHash que cambia/@vite/client
El problema · 2.1

Dos formas distintas de fallar sin conexión

En la Sesión 29 el sw.js manual listaba CORE_ASSETS a mano. Eso funcionaba para archivos con nombre fijo, pero fallaba en los dos escenarios reales:

En desarrollo (npm run dev)

Vite sirve /src/main.ts y /@vite/client al vuelo. No son archivos reales — no se pueden precachear.

En build real (npm run build)

npm run build genera un bundle con un hash que cambia en cada compilación — imposible de escribir a mano de forma estable.

El problema · 2.2

Por qué instalamos vite-plugin-pwa

No escribimos el bundle a mano en globPatterns: ese plugin ejecuta Workbox después de que Vite termina su propio build, cuando los nombres de archivo con hash ya existen de verdad. La lista de precaché nunca queda desactualizada porque nunca se escribió a mano — se lee del resultado real del build, cada vez.

Configuración · 3.2

vite.config.ts: qué le pedimos a Workbox

vite.config.ts
import { defineConfig } from 'vite';
import { VitePWA } from 'vite-plugin-pwa';

export default defineConfig({
  plugins: [
    VitePWA({
      manifest: false,
      registerType: 'autoUpdate',
      injectRegister: false, // registramos nosotros mismos en main.ts
      workbox: {
        globPatterns: ['**/*.{html,js,css,png,json}'],
        // ... runtimeCaching: ver la lámina siguiente
      },
    }),
  ],
});

Configuración · 3.3

main.ts: el módulo virtual reemplaza al register() manual

main.ts
import { registerSW } from 'virtual:pwa-register';

registerSW({
  immediate: true,
  onRegisteredSW(swUrl, registration) {
    console.log('SW de Workbox registrado:', swUrl, registration);
  },
  onRegisterError(error) {
    console.error('Error al registrar el SW de Workbox:', error);
  },
});
En vez de navigator.serviceWorker.register('/sw.js') a mano, se usa el módulo virtual que el plugin provee. También hace falta agregar /// <reference types="vite-plugin-pwa/client" /> en src/vite-env.d.ts, para que TypeScript reconozca virtual:pwa-register.

El build real · 4.3

La respuesta a la Sesión 29: revision vs. revision: null

revision calculadoindex.html, manifest.json, los íconos — Workbox calculó el hash de su contenido, igual que hizo con el Gestor de Tareas en la Sesión 23.
revision: nullassets/index-DDQN0Bif.js — ese nombre YA incluye el hash de Vite (DDQN0Bif). Workbox no necesita calcular nada más.
Aquí está la respuesta a la Sesión 29: si el contenido de index-DDQN0Bif.js cambia, Vite le pone un nombre distinto en el próximo build, y la URL cambia sola. Nadie escribió ese nombre a mano, y nadie tiene que actualizarlo a mano tampoco.

Con el build de esta sesión, la página recarga completa sin conexión — título, estilos y la demo de progreso de la Sesión 33 siguen ahí.

Sesión 29 — sw.js manual

Esta misma prueba (build + preview + Offline + recargar) dejaba la pantalla en blanco.

Sesión 34 — Workbox + vite-plugin-pwa

Verificación · 5.3

Una limitación que sigue existiendo, y es honesta

IndexedDB (Sesión 33) no es parte del precaché — los datos que ya estaban guardados localmente siguen disponibles sin conexión porque IndexedDB vive en el disco del usuario, independiente del Service Worker, pero cualquier operación que dependiera de red (no hay ninguna todavía en este proyecto) seguiría sin funcionar offline.

Lo que esta sesión resuelve es el shell de la aplicación — HTML, CSS, JS, íconos — no una sincronización con un servidor que este proyecto, hoy, no tiene.

Resumen y próxima sesión

  • Workbox, sus módulos y GenerateSW/InjectManifest se estudiaron a fondo en la Sesión 23 — hoy solo se aplican al Atlas 3D, sin repetir la teoría.
  • vite-plugin-pwa ejecuta Workbox DESPUÉS del build de Vite, cuando los nombres de archivo con hash ya existen — por eso la lista de precaché nunca se escribe a mano ni queda desactualizada.
  • En el sw.js generado, los archivos con nombre fijo (HTML, manifest, íconos) llevan un revision calculado por Workbox; los archivos que Vite ya nombra con hash (assets/index-DDQN0Bif.js) llevan revision: null, porque el nombre del archivo ya hace ese trabajo.
  • La verificación de offline real se hace contra npm run build + npm run preview, nunca contra npm run dev — y, verificado hoy, el Atlas 3D recarga completo sin conexión por primera vez.
  • Esto cierra la limitación documentada desde la Sesión 29: lo que antes era "cada recurso usa la estrategia correcta" ahora sí es "la aplicación funciona sin conexión de verdad".
