Workbox en el proyecto

Migramos el Service Worker manual del Atlas 3D a Workbox, integrado al build de Vite con vite-plugin-pwa — y verificamos, de verdad, que ahora sí funciona sin conexión. Esto cierra la limitación abierta desde la Sesión 29.

Objetivos de aprendizaje

  • ✓Reemplazar el sw.js escrito a mano por uno generado con Workbox, integrado al build de Vite mediante vite-plugin-pwa.
  • ✓Explicar por qué un precaché generado después del build resuelve el problema del bundle con hash que no se podía escribir a mano desde la Sesión 29.
  • ✓Verificar, contra el build real (no el servidor de desarrollo), que el Atlas 3D funciona sin conexión de verdad por primera vez.

Recursos de esta sesión

  • Descargar .zipCheckpoint — cierre de la Sesión 33. El Atlas 3D con IndexedDB, favoritos y la nota de estudio cifrada ya integrados. Hoy reemplazamos el Service Worker manual por uno generado con Workbox — esa es la única pieza que cambia.

1Esto ya lo viste a fondo en la Sesión 23

Qué es Workbox, sus módulos, la diferencia entre GenerateSW e InjectManifest, compatibilidad de navegadores, UX/UI y Lighthouse, ya lo estudiaste con calma en la Sesión 23, sobre el Gestor de Tareas. No repetimos nada de esa teoría aquí.

Lo que sí toca hoy es distinto, y es el motivo por el que esta sesión importa más que un simple "aplicarlo al proyecto": el Gestor de Tareas no tiene bundler, así que Workbox generó su sw.js leyendo archivos planos. El Atlas 3D sí tiene un bundler — Vite — y es exactamente ese bundler el que rompió el offline manual en la Sesión 29. Hoy vemos por qué Workbox integrado al build sí lo resuelve.

2Recordando el problema exacto de la Sesión 29

En la Sesión 29 el sw.js manual listaba CORE_ASSETS a mano. Eso funcionaba para archivos con nombre fijo, pero npm run build genera un bundle con un hash que cambia en cada compilación — imposible de escribir a mano de forma estable. En modo desarrollo, la situación era todavía peor: Vite sirve /src/main.ts y /@vite/client al vuelo, y esos no son archivos reales que se puedan precachear.

Por eso instalamos vite-plugin-pwa y no escribimos el bundle a mano en globPatterns: ese plugin ejecuta Workbox después de que Vite termina su propio build, cuando los nombres de archivo con hash ya existen de verdad. La lista de precaché nunca queda desactualizada porque nunca se escribió a mano — se lee del resultado real del build, cada vez.

3Instalación y configuración

Terminal
npm install -D vite-plugin-pwa
vite.config.ts
import { defineConfig } from 'vite';
import { VitePWA } from 'vite-plugin-pwa';

export default defineConfig({
  plugins: [
    VitePWA({
      // El manifest ya existe a mano desde la Sesión 27 — aquí solo
      // pedimos a Workbox que genere el Service Worker, no el manifest.
      manifest: false,
      registerType: 'autoUpdate',
      injectRegister: false, // registramos nosotros mismos en main.ts
      workbox: {
        // Esto es lo que resuelve la Sesión 29: la lista de precaché se
        // genera a partir de dist/ DESPUÉS del build, con los nombres de
        // archivo reales (con hash incluido) — nunca escrita a mano.
        globPatterns: ['**/*.{html,js,css,png,json}'],
        runtimeCaching: [
          {
            urlPattern: /\/iconos\//,
            handler: 'CacheFirst',
            options: { cacheName: 'imagenes', expiration: { maxEntries: 60, maxAgeSeconds: 30 * 24 * 60 * 60 } },
          },
          { urlPattern: /\/api\//, handler: 'NetworkFirst', options: { cacheName: 'api-atlas3d' } },
        ],
      },
    }),
  ],
});

El sw.js manual de las Sesiones 28-32 se elimina de public/ — lo genera el plugin dentro de dist/ en cada build. El registro también cambia: en vez de navigator.serviceWorker.register('/sw.js') a mano, se usa el módulo virtual que el plugin provee:

main.ts
import { registerSW } from 'virtual:pwa-register';

registerSW({
  immediate: true,
  onRegisteredSW(swUrl, registration) {
    console.log('SW de Workbox registrado:', swUrl, registration);
  },
  onRegisterError(error) {
    console.error('Error al registrar el SW de Workbox:', error);
  },
});
También hace falta agregar /// <reference types="vite-plugin-pwa/client" /> en src/vite-env.d.ts, para que TypeScript reconozca el módulo virtual virtual:pwa-register.

Y así se ve, dentro de dist/sw.js, la lista de precaché que Workbox generó a partir de esos archivos reales:

dist/sw.js (fragmento, formateado)
precacheAndRoute([
  { url: "manifest.json", revision: "1aa61cc8ef180b7e9a1d14c45f81f46c" },
  { url: "index.html", revision: "97366fdbf8c3745fe1945cc2b14f85dd" },
  { url: "iconos/icon-512.png", revision: "bebb48aabd0d797c05f250f20e26cd85" },
  { url: "iconos/icon-512-maskable.png", revision: "c380a180109dea2bb27a3ca6875be047" },
  { url: "iconos/icon-192.png", revision: "a9b0715397c6ecd59ca5eeb1250af77d" },
  { url: "assets/index-DDQN0Bif.js", revision: null },
  { url: "assets/index-COBG-ZA2.css", revision: null },
  { url: "assets/workbox-window.prod.es5-BqEJf4Xk.js", revision: null },
]);
Aquí está la respuesta a la Sesión 29: index.html, manifest.json y los íconos sí llevan un revision — Workbox calculó el hash de su contenido, igual que hizo con el Gestor de Tareas en la Sesión 23. Pero assets/index-DDQN0Bif.js tiene revision: null — porque ese nombre de archivo YA incluye el hash de Vite (DDQN0Bif). Workbox no necesita calcular nada más: si el contenido cambia, Vite le pone un nombre distinto en el próximo build, y la URL cambia sola. Nadie escribió index-DDQN0Bif.js a mano, y nadie tiene que actualizarlo a mano tampoco.

5Verificando que ahora sí funciona sin conexión

La verificación tiene que ser contra el build real — el servidor de desarrollo (npm run dev) sigue sin tener un Service Worker útil para esto, tal como se explicó en la Sesión 29:

Terminal
npm run build
npm run preview
  • Abre la URL que imprime vite preview (normalmente http://localhost:4173).
  • DevTools → Application → Service Workers: debe aparecer activo y con el scope correcto.
  • DevTools → Network → casilla Offline.
  • Recarga la página (F5 o Ctrl+R).
Resultado real, verificado: con el build de esta sesión, la página recarga completa sin conexión — título, estilos y la demo de progreso de la Sesión 33 siguen ahí. Esta misma prueba, contra el sw.js manual de la Sesión 29, dejaba la pantalla en blanco. La diferencia es exactamente la pieza que cambió hoy.

Una limitación que sigue existiendo, y es honesta: IndexedDB (Sesión 33) no es parte del precaché — los datos que ya estaban guardados localmente siguen disponibles sin conexión porque IndexedDB vive en el disco del usuario, independiente del Service Worker, pero cualquier operación que dependiera de red (no hay ninguna todavía en este proyecto) seguiría sin funcionar offline. Lo que esta sesión resuelve es el shell de la aplicación — HTML, CSS, JS, íconos — no una sincronización con un servidor que este proyecto, hoy, no tiene.

Resumen de la sesión

  • Workbox, sus módulos y GenerateSW/InjectManifest se estudiaron a fondo en la Sesión 23 — hoy solo se aplican al Atlas 3D, sin repetir la teoría.
  • vite-plugin-pwa ejecuta Workbox DESPUÉS del build de Vite, cuando los nombres de archivo con hash ya existen — por eso la lista de precaché nunca se escribe a mano ni queda desactualizada.
  • En el sw.js generado, los archivos con nombre fijo (HTML, manifest, íconos) llevan un revision calculado por Workbox; los archivos que Vite ya nombra con hash (assets/index-DDQN0Bif.js) llevan revision: null, porque el nombre del archivo ya hace ese trabajo.
  • La verificación de offline real se hace contra npm run build + npm run preview, nunca contra npm run dev — y, verificado hoy, el Atlas 3D recarga completo sin conexión por primera vez.
  • Esto cierra la limitación documentada desde la Sesión 29: lo que antes era "cada recurso usa la estrategia correcta" ahora sí es "la aplicación funciona sin conexión de verdad".
