SECCIÓN 01

De "dejar pasar" a interceptar de verdad

event.respondWith() decide de dónde viene la respuesta — del caché, de la red, o de ambos.

event.respondWith()
Interceptar de verdad · 1.1

Lo que event.respondWith() controla de verdad

Pasarle directamente fetch(event.request), como hicimos en la Sesión 28, es una respuesta válida — pero ignora por completo el caché que install ya construyó. La petición sigue yendo a la red aunque el recurso ya esté guardado localmente.

Interceptar de verdad significa decidir, dentro del propio manejador de fetch, de dónde viene la respuesta: del caché, de la red, o de una combinación de ambas.

Esa decisión es, en el fondo, una estrategia de caché — hoy construimos la más simple posible, sobre el sw.js del Atlas 3D.
SECCIÓN 02

caches.match(): responder desde el caché

Busca una respuesta guardada en cualquier caché del origen — o undefined si no hay coincidencia.

caches.match(request)
caches.match() · 2.1

Responder desde el caché

sw.js (fragmento)
self.addEventListener('fetch', event => {
  event.respondWith(
    caches.match(event.request).then(encontrado => {
      // encontrado es un Response, o undefined
      return encontrado;
    })
  );
});
Incompleto a propósito: si encontrado es undefined, la petición fallaría. La lista completa de la interfaz Cache llega más adelante en el Sub-bloque B.
SECCIÓN 03

Cachear las primeras rutas

Las mismas tres rutas que el install de la Sesión 28 ya guardó — el shell mínimo del Atlas 3D.

CORE_ASSETS
Cachear las primeras rutas · 3.1

Cuáles, y por qué esas y no otras

"Las primeras rutas" son, literalmente, las de CORE_ASSETS: '/', '/index.html' y '/manifest.json' — el shell mínimo del Atlas 3D. Todavía no hay un CSS o JS propios que cachear por separado, como sí tenía el Gestor de tareas.

Lo que no cacheamos hoy: rutas dinámicas, respuestas de una API, o cualquier recurso que cambie con frecuencia.

Cachear ese tipo de rutas sin una estrategia pensada puede dejar al usuario viendo datos viejos indefinidamente — el tema exacto de las 5 estrategias más adelante en el Sub-bloque B.
SECCIÓN 04

Una estrategia básica de respuesta

Caché primero, red si no está — sin escribir nada nuevo al caché todavía.

encontrado || fetch(event.request)
Estrategia básica · 4.1

encontrado || fetch(event.request)

sw.js (fragmento)
self.addEventListener('fetch', event => {
  event.respondWith(
    caches.match(event.request).then(
      encontrado => encontrado || fetch(event.request)
    )
  );
});
Para las tres rutas de CORE_ASSETS, la respuesta ahora viene del disco del usuario, no de la red — pero eso todavía no es lo mismo que "funciona sin conexión". Sigue leyendo.
SECCIÓN 05

Caso real: el sw.js actualizado del Atlas 3D

install y activate quedan igual — el único cambio real está en fetch.

sw.js completo
Caso real · 5.1

El sw.js completo

public/sw.js
const CACHE_NAME = 'atlas3d-v1';
const CORE_ASSETS = ['/', '/index.html', '/manifest.json'];

self.addEventListener('install', event => {
  event.waitUntil(caches.open(CACHE_NAME).then(cache => cache.addAll(CORE_ASSETS)));
});

self.addEventListener('activate', event => {
  event.waitUntil(self.clients.claim());
});

self.addEventListener('fetch', event => {
  event.respondWith(
    caches.match(event.request).then(
      encontrado => encontrado || fetch(event.request)
    )
  );
});
El único cambio frente a la Sesión 28 está en el manejador de fetch — install y activate quedan idénticos.
Caso real · 5.2

Verificar en DevTools

DevTools
// F12 → Network → recarga la página del Atlas 3D
// Busca la fila de index.html o manifest.json
//
// Columna "Size": debe decir (ServiceWorker)
// en vez de un tamaño en KB
Esa palabra es la prueba de que la respuesta vino del caché, no de la red. Una ruta fuera de CORE_ASSETS (como /src/main.ts) sí debería mostrar su tamaño normal.
Caso real · 5.3

¿Por qué no funciona sin conexión todavía?

En desarrollo (npm run dev)

/src/main.ts y /@vite/client no son archivos reales: el servidor de Vite los genera al vuelo. No se pueden listar en CORE_ASSETS, así que sin red fallan — main.ts nunca corre y la pantalla queda en blanco.

En build real (npm run build)

Vite nombra el bundle con un hash que cambia en cada build (assets/index-BXm8pqCz.js). Ese nombre no existe hasta compilar — no se puede escribir a mano en CORE_ASSETS, y mañana ya no coincidiría.

No es un error de tu código: es la razón exacta por la que un proyecto con empaquetador genera su lista de precaché automáticamente en vez de escribirla a mano. Eso es Workbox — Sesión 34, espejo de la Sesión 23.

Resumen de la lección

  • Pasar la petición directo a fetch() es válido, pero ignora el caché — no es interceptar de verdad.
  • caches.match(request) busca una respuesta guardada; devuelve el Response o undefined.
  • La estrategia de hoy: encontrado || fetch(event.request) — caché primero, red si no está, sin escribir nada nuevo.
  • Solo cacheamos las primeras rutas del Atlas 3D — nada dinámico todavía.
  • En DevTools → Network, una respuesta servida desde el Service Worker se marca (ServiceWorker) en la columna Size.
  • Todavía no funciona sin conexión de verdad: ni en desarrollo (/src/main.ts) ni en build real (bundle con hash) — eso lo resuelve Workbox, en la Sesión 34.
