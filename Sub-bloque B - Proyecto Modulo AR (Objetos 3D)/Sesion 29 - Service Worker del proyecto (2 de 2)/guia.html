Service Worker del proyecto (2/2)

La Sesión 28 dejó un Service Worker del Atlas 3D que registra un manejador de fetch, pero deja pasar cada petición sin tocarla. Hoy lo interceptamos de verdad: respondemos desde el caché cuando podemos, aplicando sobre tu propio proyecto exactamente la misma estrategia mínima de la Sesión 18. Las 5 estrategias completas, con nombre, llegan más adelante en el Sub-bloque B.

1Bienvenida y recap

En la Sesión 28 registramos el Service Worker del Atlas 3D y completamos su ciclo de vida — install cachea los recursos esenciales ('/', '/index.html' y '/manifest.json') con cache.addAll(), activate reclama el control con clients.claim(), y fetch... deja pasar cada petición directo a la red, sin tocarla. Cumplía el requisito de instalabilidad, pero no hacía nada útil todavía. Hoy cambiamos exactamente eso — aplicando sobre tu propio proyecto lo mismo que ya viste en la Sesión 18 sobre el Gestor de tareas.

Dato clave: el install de la Sesión 28 ya guardó en caché CORE_ASSETS del Atlas 3D: '/', '/index.html' y '/manifest.json'. Hoy no cacheamos nada nuevo — usamos lo que ya está ahí, el mismo principio de la Sesión 18.

2De "dejar pasar" a interceptar de verdad

event.respondWith() es la llamada que de verdad controla qué recibe la página como respuesta a su petición. Pasarle directamente fetch(event.request), como hicimos en la Sesión 28, es una respuesta válida — pero ignora por completo el caché que el evento install ya construyó. La petición sigue yendo a la red aunque el recurso ya esté guardado localmente.

Interceptar de verdad significa decidir, dentro del propio manejador de fetch, de dónde viene la respuesta: del caché, de la red, o de una combinación de ambas. Esa decisión es, en el fondo, lo que se llama una estrategia de caché — hoy construimos la más simple posible, sobre el sw.js del Atlas 3D.

3caches.match(): responder desde el caché

caches.match(request) busca, en todos los cachés del origen, una respuesta guardada que coincida con la petición dada. Devuelve una promesa: se resuelve con el Response encontrado, o con undefined si no hay coincidencia [1].

sw.js (fragmento)
self.addEventListener('fetch', event => {
  event.respondWith(
    caches.match(event.request).then(encontrado => {
      // encontrado es un Response, o undefined
      return encontrado;
    })
  );
});

Este fragmento por sí solo está incompleto a propósito: si encontrado es undefined (la ruta no está en caché), la respuesta sería undefined y la petición fallaría. Falta la segunda mitad — qué hacer cuando no está en caché — y eso es exactamente la sección siguiente.

Dato clave: caches.match() es la contraparte de lectura de cache.addAll(). La lista completa de operaciones de la interfaz Cache — put(), delete(), keys() y el resto — llega más adelante en el Sub-bloque B, aplicada al Atlas 3D.

4Cachear las primeras rutas del Atlas 3D

"Las primeras rutas" son, literalmente, las que la Sesión 28 ya dejó en CORE_ASSETS: '/', '/index.html' y '/manifest.json' — el shell mínimo del proyecto. Son las rutas que, si fallan, la aplicación ni siquiera puede dibujarse en pantalla. Por eso se cachean en install, antes de que exista ninguna petición real del usuario.

A diferencia del Gestor de tareas de la Sesión 18, el Atlas 3D todavía no tiene un estilos.css ni un app.js propios para cachear por separado: hoy todo lo que existe en el proyecto son esas tres rutas. A medida que el proyecto crezca — nuevos archivos en src/, y más adelante un bundle de producción — la lista de CORE_ASSETS crece con él, pero eso no es el tema de hoy. Lo que tampoco cacheamos hoy: rutas dinámicas, respuestas de una API, o cualquier recurso que cambie con frecuencia. Cachear ese tipo de rutas sin una estrategia pensada puede dejar al usuario viendo datos viejos indefinidamente — ese cuidado llega, con nombre propio, más adelante en el Sub-bloque B.

5Una estrategia básica de respuesta

Uniendo las dos piezas anteriores: si la petición está en caché, respondemos con eso; si no, vamos a la red. Nada más — hoy no escribimos nada nuevo en el caché durante fetch; eso y las otras estrategias con nombre (Cache Only, Network Only, Network First, Stale-While-Revalidate) llegan formalmente más adelante en el Sub-bloque B.

sw.js (fragmento)
self.addEventListener('fetch', event => {
  event.respondWith(
    caches.match(event.request).then(
      encontrado => encontrado || fetch(event.request)
    )
  );
});

encontrado || fetch(event.request) es la forma corta de decir "si hay algo en caché, úsalo; si no, ve a la red". Para las tres rutas de CORE_ASSETS del Atlas 3D, la respuesta ahora viene del disco del usuario, no de la red — pero eso todavía no es lo mismo que "tu proyecto funciona sin conexión": lo que se ve en pantalla depende de más piezas que esas tres rutas, y esa distinción es justamente el tema de la sección siguiente.

6Caso real: el sw.js actualizado del Atlas 3D

El único cambio real de hoy frente a la Sesión 28 es el manejador de fetch. CACHE_NAME, CORE_ASSETS, install y activate quedan exactamente igual:

public/sw.js
const CACHE_NAME = 'atlas3d-v1';
const CORE_ASSETS = [
  '/',
  '/index.html',
  '/manifest.json',
];

self.addEventListener('install', event => {
  event.waitUntil(
    caches.open(CACHE_NAME).then(cache => cache.addAll(CORE_ASSETS))
  );
});

self.addEventListener('activate', event => {
  event.waitUntil(self.clients.claim());
});

self.addEventListener('fetch', event => {
  event.respondWith(
    caches.match(event.request).then(
      encontrado => encontrado || fetch(event.request)
    )
  );
});

Para verificarlo: F12 → pestaña Network → recarga la página del Atlas 3D. Busca la fila de index.html o manifest.json: en la columna "Size" debería decir (ServiceWorker) en vez de un tamaño en KB — esa palabra es la prueba de que la respuesta vino del caché, no de la red. Compáralo con una petición que no esté en CORE_ASSETS (por ejemplo, /src/main.ts servido por Vite): esa sí debería mostrar su tamaño normal, porque cae al fetch() de respaldo.

Por qué la pantalla queda en blanco si marcas "Offline" y recargas: las tres rutas de CORE_ASSETS sí se sirven desde el caché — eso es real, y lo acabas de comprobar. Pero lo que dibuja el <h1> en pantalla es src/main.ts, que el servidor de desarrollo de Vite sirve como /src/main.ts (junto con /@vite/client, para el recargado en caliente) — y ninguno de los dos es un archivo real que puedas listar en CORE_ASSETS: el servidor los genera al vuelo, cada vez, mientras corre npm run dev. Sin red esa petición falla, main.ts nunca se ejecuta, y la página se queda con el <div id="app"> vacío. No es un error tuyo ni de tu sw.js — es esperable en modo desarrollo.

¿Y probando contra el build real, con npm run build y npm run preview en vez de npm run dev? Tampoco funciona todavía, por una razón distinta. Vite empaqueta tu proyecto en un archivo con un hash en el nombre — algo como assets/index-BXm8pqCz.js — que cambia en cada build. Ese nombre no existe hasta que compilas, así que no lo puedes escribir a mano en CORE_ASSETS: y aunque lo escribieras hoy, en el próximo build ya no coincidiría. Esto no es una limitación de tu código — es la razón exacta por la que, en un proyecto con empaquetador, la lista de precaché no se escribe a mano: se genera automáticamente a partir del build real. Eso es exactamente lo que hace Workbox, y ya está en tu ruta: la Sesión 34 (espejo de la Sesión 23) lo aplica sobre este mismo proyecto.

  • Pasar la petición directo a fetch() es válido, pero ignora el caché — no es interceptar de verdad.
