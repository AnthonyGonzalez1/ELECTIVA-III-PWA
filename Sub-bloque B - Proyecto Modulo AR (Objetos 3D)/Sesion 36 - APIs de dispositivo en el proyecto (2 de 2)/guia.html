APIs de dispositivo en el proyecto (2/2)

La cámara se convierte en el fondo vivo del visor 3D: el primer paso hacia la realidad aumentada de las próximas sesiones. Es el espejo de la Sesión 24 — pero un flujo de video abierto es una responsabilidad distinta a una foto, y hoy se nota.

Objetivos de aprendizaje

  • ✓Colocar el video de la cámara como fondo vivo detrás del canvas de Three.js, con las dos capas bien apiladas.
  • ✓Explicar por qué la transparencia del canvas se decide al crear el renderer (alpha: true) y qué papel juega scene.background.
  • ✓Gestionar el ciclo de vida de un flujo de video abierto: apagarlo al salir de la página y al terminar, y degradar con elegancia si el permiso se niega.
  • ✓Distinguir, con honestidad, "un modelo dibujado sobre la cámara" de la realidad aumentada de verdad.

Recursos de esta sesión

  • Descargar .zipCheckpoint — cierre de la Sesión 35. El Atlas 3D con su primer visor de Three.js (cubo de prueba) controlado por sensores de orientación, con OrbitControls como respaldo. Hoy le agregamos camara.ts y la cámara como fondo.

1Esto ya lo viste a fondo en la Sesión 24

El modelo de permisos (contexto seguro, gesto del usuario, estados granted/denied/prompt), getUserMedia y sus constraints (ideal contra exact), los errores (NotAllowedError, NotFoundError, NotReadableError, TypeError en HTTP) y la obligación de detener las pistas, se estudiaron a fondo en la Sesión 24, sobre el Gestor de Tareas. Aquí no se repiten.

La diferencia que importa hoy es de duración. En el Gestor la cámara se abría un instante, tomaba una foto y se cerraba. En el Atlas 3D el flujo queda abierto todo el tiempo como fondo del visor — y eso convierte detalles menores en problemas reales: batería, LED encendido, y qué pasa cuando el usuario cambia de pestaña.

2Dos capas: video detrás, canvas encima

La idea es la más simple posible: un <video> ocupando todo el contenedor, y el <canvas> de Three.js apilado encima. Si el canvas es transparente donde no hay modelo, se ve el video a través de él. En el HTML, el video vive dentro del mismo contenedor que el visor, oculto hasta que haya cámara:

index.html y style.css (fragmentos)
<div id="visor" class="visor">
  <video id="fondo-camara" class="fondo-camara" playsinline muted hidden></video>
</div>

.visor { position: relative; background: #0b1220; }
.fondo-camara { position: absolute; inset: 0; width: 100%; height: 100%; object-fit: cover; }
.fondo-camara[hidden] { display: none; }
.visor canvas { position: relative; z-index: 1; }

object-fit: cover hace que el video llene el contenedor sin deformarse (recortando lo que sobre). playsinline evita que iOS lo abra a pantalla completa, y muted es necesario: sin sonido, el navegador permite reproducirlo sin que haya un gesto previo. Y la regla [hidden] existe por una razón práctica: al darle display propio a una clase, el atributo hidden deja de ocultar el elemento; hay que restituirlo.

3La transparencia: dos decisiones, en lugares distintos

Que el canvas deje ver el video depende de dos cosas, y fallar en cualquiera deja la pantalla con el fondo oscuro de siempre:

  1. El renderer debe crearse con alpha: true. Es una decisión de creación: el contexto WebGL se configura con o sin canal alfa una sola vez. Si lo creaste sin alfa, ningún ajuste posterior lo vuelve transparente.
  2. scene.background debe ser null mientras la cámara esté activa. Mientras tenga un color, Three.js pinta ese color opaco sobre todo el canvas y tapa el video.
src/visor.ts (fragmentos)
const COLOR_FONDO = new THREE.Color(0x0b1220);
escena.background = COLOR_FONDO;

// alpha se decide AL CREAR el renderer (no se puede cambiar después)
const renderer = new THREE.WebGLRenderer({ antialias: true, alpha: true });
renderer.setClearColor(0x000000, 0);          // limpiar con alfa 0 = transparente

// ... dentro del objeto que devuelve crearVisor():
fondoTransparente(activo: boolean) {
  escena.background = activo ? null : COLOR_FONDO;
},

Fíjate en la asimetría: alpha se fija al crear, pero el fondo se alterna en caliente. Por eso el renderer se crea siempre con alfa, aunque en la Sesión 35 no se necesitaba, y la cámara solo cambia scene.background.

4La cámara como fondo: camara.ts

src/camara.ts
export async function iniciarCamaraDeFondo(video: HTMLVideoElement): Promise<MediaStream> {
  const stream = await navigator.mediaDevices.getUserMedia({
    video: { facingMode: { ideal: "environment" }, width: { ideal: 1280 }, height: { ideal: 720 } },
    audio: false,
  });
  video.srcObject = stream;
  await video.play();
  return stream;
}

export function detenerCamaraDeFondo(video: HTMLVideoElement, stream: MediaStream | null): void {
  stream?.getTracks().forEach((pista) => pista.stop());
  video.srcObject = null;
}

Es la misma llamada de la Sesión 24, con facingMode: { ideal: "environment" } (cámara trasera si existe; si no, la que haya), sin audio y sin capturar fotos: aquí solo se muestra. El botón del visor la activa dentro del clic, y un segundo clic la apaga.

5Ciclo de vida: apagarla a tiempo

Un flujo abierto que nadie mira es un problema: gasta batería, mantiene el LED de la cámara encendido, y le dice al usuario "esta app te está grabando" cuando ya ni la está usando. La regla razonable: apagar la cámara cuando la página deja de estar visible. El evento visibilitychange avisa cuando el usuario cambia de pestaña o minimiza el navegador:

src/main.ts (fragmento)
document.addEventListener("visibilitychange", () => {
  if (document.hidden && streamFondo) {
    apagarCamara();
    avisarVisor("La cámara se apagó al salir de la página. Vuelve a activarla cuando quieras.");
  }
});

Decisión de diseño: no se reactiva sola al volver. Reactivarla sin un clic implicaría volver a abrir la cámara sin que el usuario lo pida, justo lo que la Sesión 24 enseñó a evitar. El mensaje le dice qué pasó y qué hacer.

Una corrección que salió de leer la documentación. Mi primer borrador de describirErrorCamara asociaba SecurityError con "solo funciona en HTTPS". Al contrastarlo con MDN resultó falso: en una página HTTP, navigator.mediaDevices es undefined y lo que se lanza es TypeError; SecurityError significa otra cosa (el navegador tiene deshabilitado el acceso a medios en ese documento). El código de hoy y el checkpoint de la Sesión 24 ya llevan el mapeo corregido.

6Verificado contra el build real

Todo se ejecutó contra npm run build + npm run preview, en Chromium con una cámara falsa (el navegador genera un video sintético), con WebGL por software. Salida literal:

$ npm run build
dist/assets/index-BfFPq1Qd.js   501.10 kB │ gzip: 127.34 kB
✓ built in 2.16s
precache 8 entries (508.80 KiB)

$ node test_s36.js
boton: 📷 Cámara: ACTIVA (toca para apagar)
video: { hidden: false, w: 1280, h: 720, reproduciendo: true, pistasVivas: 1 }
al ocultar la pagina -> boton: 📷 Cámara de fondo | srcObject null: true | aviso: La cámara se apagó al salir de la página. Vuelve a activarla cuando quieras.
DENEGADA -> Bloqueaste el permiso de cámara. El visor sigue funcionando sin ella. | visor sigue (canvas): 1
errores: []
Qué demuestra: (1) con la cámara activa, el video llega a 1280×720, se reproduce y hay una pista viva; (2) al ocultarse la página, el botón vuelve a su estado inicial, el video queda sin fuente (srcObject es null) y el usuario ve el aviso; (3) con el permiso denegado, el mensaje es claro y el visor sigue con su canvas — la función es una mejora, no un requisito; (4) cero errores de página.

Y se vio, no solo se midió. Una captura de pantalla de la página con la cámara activa mostró el cubo dorado dibujado sobre el video sintético verde del navegador, con los bordes del cubo nítidos y el video visible alrededor — es decir, el canvas era transparente donde no había modelo. Sin la cámara, el mismo visor mostraba el fondo azul oscuro.

Límites honestos de esta prueba: (1) el "cambio de pestaña" se simuló fijando document.hidden y disparando visibilitychange; no se cambió de pestaña de verdad. (2) La cámara es sintética: no se probó la cámara trasera de un teléfono, ni cómo object-fit: cover recorta una imagen vertical real. (3) No se midió el consumo de batería. Esas tres comprobaciones son de la actividad de hoy.

7Esto todavía NO es realidad aumentada

Con la cámara de fondo y el cubo encima, el aviso de la pantalla lo dice: el cubo no está anclado a nada del mundo. Si mueves el teléfono, el cubo se queda donde está dentro del canvas, no sobre la mesa que estás viendo. Lo que tenemos es un fondo de video y un modelo 3D dibujado encima — la base sobre la que se construye la realidad aumentada, no la realidad aumentada. Para que un objeto parezca estar en la mesa hace falta saber dónde está la cámara en el espacio y cómo se mueve (seguimiento), algo que ni la cámara ni los sensores de hoy resuelven por sí solos. Cómo se logrará en este proyecto se decide en las sesiones de realidad aumentada.

Por la misma razón, de la Sesión 24 no se aplica hoy la ubicación: ninguna parte del Atlas 3D la necesita todavía, y pedir un permiso que no se usa es lo contrario de lo que enseña esa sesión.

8Probar en un teléfono real

Aplica lo mismo que en las dos sesiones anteriores: la cámara solo existe en contexto seguro, así que npm run dev por la red local (HTTP) no sirve en el teléfono. Usa uno de los caminos de la Sesión 24, sección 9 sirviendo el build (npm run build + npm run preview detrás de un túnel o reenvío de puerto), no el servidor de desarrollo. Con facingMode: { ideal: "environment" } deberías ver la cámara trasera.

Resumen de la sesión

  • El permiso, los errores y las constraints de getUserMedia ya se estudiaron en la Sesión 24; hoy se aplican sobre un flujo que queda abierto, no sobre una foto.
  • El fondo de cámara son dos capas: un <video> con object-fit: cover detrás, y el canvas de Three.js encima.
  • La transparencia exige alpha: true al crear el renderer y scene.background = null mientras la cámara esté activa.
  • Un flujo abierto se apaga cuando la página deja de ser visible (visibilitychange) y no se reactiva sin un clic.
  • Verificado contra el build real con cámara sintética: 1280×720, pista viva, apagado al ocultarse, permiso denegado sin romper el visor — y cubo visible sobre el video en la captura.
  • Esto es la base de la realidad aumentada, no la RA: el cubo no está anclado al mundo. Quedan por probar en hardware real la cámara trasera, el recorte de video vertical y la batería.
